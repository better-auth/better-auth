Better Auth comes with a built-in CLI to help you manage the database schemas, create initial admin users, initialize your project, generate a secret key for your application, and gather diagnostic information about your setup.

## Generate

The `generate` command creates the schema required by Better Auth. If you're using a database adapter like Prisma or Drizzle, this command will generate the right schema for your ORM. If you're using the built-in Kysely adapter, it will generate an SQL file you can run directly on your database.

```package-install title="Terminal"
npx auth@latest generate
```

### Options

* `--output` - Where to save the generated schema. For Prisma, it will be saved in prisma/schema.prisma. For Drizzle, it goes to schema.ts in your project root. For Kysely, it's an SQL file saved as schema.sql in your project root.
* `--config` - The path to your Better Auth config file. By default, the CLI will search for an auth.ts file in **./**, **./utils**, **./lib**, or any of these directories under the `src` directory.
* `--yes` - Skip the confirmation prompt and generate the schema directly.

## Migrate

The `migrate` command applies the Better Auth schema directly to your database. It supports the built-in SQL database configuration and SQL-backed Drizzle or Prisma adapters. Use `generate` and your own migration tooling for other adapters.

```package-install title="Terminal"
npx auth@latest migrate
```

### Options

* `--config` - The path to your Better Auth config file. By default, the CLI will search for an auth.ts file in **./**, **./utils**, **./lib**, or any of these directories under the `src` directory.
* `--yes` - Skip the confirmation prompt and apply the schema directly.
* `--dry-run` - Inspect the migration without changing the database.
* `--json` - Print a deterministic, machine-readable migration plan without changing the database.
* `--plan <file>` - Apply the reviewed release decisions recorded in a `better-auth-migration.json` file.

### Inspect before applying

Use `--dry-run` before an upgrade or when reviewing a generated migration:

```package-install title="Terminal"
npx auth@latest migrate --dry-run
```

The human-readable output identifies the adapter and SQL dialect and lists the blocker codes, if any.

Use `--json` in CI or with a coding agent. The output has a versioned `formatVersion`, the detected adapter and SQL dialect under `target`, a `status`, sorted schema changes, and one entry per blocker. Each blocker carries a stable `code`, a one-sentence fix under `remediation.summary`, and the documentation anchor for that code under `remediation.docs`. A blocked plan exits with status `1`, and no database changes are applied.

```package-install title="Terminal"
npx auth@latest migrate --json > better-auth-migration-plan.json
```

After resolving every blocker, run the command again. An `up-to-date` plan means the configured schema is already present; a `ready` plan can be applied with `migrate`.

### Migrating a Better Auth 1.6 database

`migrate` recognizes 1.6 data by the shape of the blockers it finds and switches to the guided migration on its own. In a terminal, it prints the detected adapter and dialect, the populated 1.6 tables with row counts, and the account issuers resolved from your configuration. It then asks only for the decisions the configuration cannot answer: whether a table found under an undeclared name holds a retired model's 1.6 data, an issuer for each unresolvable provider, whether stored OAuth consents move or users grant them again, and confirmation of the SCIM accounts it retires. The answers are written to `better-auth-migration.json`, the full plan is shown, and one final confirmation lists every irreversible action before anything is written.

<Callout type="warn">
  When upgrading a Drizzle or Prisma project from 1.6, update the ORM schema used by your Better Auth configuration before running the migration, but do not apply that schema to the database. Drizzle users should make the adapter import the generated 1.7 schema. Prisma users should update `schema.prisma` and run `prisma generate`. Keep existing physical table and column mappings unchanged. The database must remain on the 1.6 schema until `migrate` performs the reviewed data and schema changes together.
</Callout>

Replay the same decisions on another environment, in CI, or after an interrupted run:

```package-install title="Terminal"
npx auth@latest migrate --plan better-auth-migration.json
```

```json title="better-auth-migration.json"
{
  "formatVersion": 1,
  "issuers": {
    "legacy-portal": "https://sso.example.com"
  },
  "oauth": {
    "consents": "reauthorize"
  },
  "scim": {
    "retireAccountIds": ["acc_2f9c81", "acc_71ab04"]
  },
  "legacyTableNames": {
    "oauthApplication": "oauth_app_1_6"
  }
}
```

Every key except `formatVersion` is optional; record only what your data needs. `issuers` maps a provider ID to the issuer 1.7 establishes for its existing accounts, and only for providers the tool cannot resolve from your configuration. `oauth.consents` is `"migrate"` or `"reauthorize"`, and it also acknowledges the client move and the retirement of 1.6 provider tokens. `scim.retireAccountIds` must match the accounts owned by the legacy SCIM providers exactly; those IDs are never inferred from email or provider-name patterns. `legacyTableNames` names customized physical 1.6 tables for `oauthApplication`, `oauthAccessToken`, `oauthConsent`, and `scimProvider`, and a model set to `null` records that no such table holds its data. Unknown keys and any unsupported `formatVersion` are rejected.

Without a terminal and without `--plan`, a run that still needs release decisions exits `1` with the blocker list rather than guessing.

The migration validates every decision before writing, rejecting issuers that contradict your configuration as well as identity collisions. It renames the legacy OAuth and SCIM tables with a `__better_auth_1_6` suffix before creating the 1.7 replacements. PostgreSQL, SQLite, and SQL Server run the relational data and schema cutover on one transaction-scoped connection. MySQL validates every deterministic decision before writing and uses resumable operations because MySQL can commit DDL implicitly. If a MySQL infrastructure or permission error interrupts the cutover, keep authentication writes stopped, correct the error, and rerun the same command with the same decisions file.

If Prisma Migrate or Drizzle Kit owns your versioned schema history, record this direct migration in that history before the next deployment. Do not run an ORM migration that applies the same 1.7 changes a second time. For an adapter that cannot expose a SQL migration connection, follow the [manual 1.6 to 1.7 migration](/docs/guides/1-7-manual-migration).

### Blocker codes

A blocked run changes nothing. Each code links to its remediation in the [1.7 upgrade guide](/docs/guides/1-7-upgrade-guide#migration-blockers):

* [`account-identity-collision`](/docs/guides/1-7-upgrade-guide#account-identity-collision) - Two account rows would share one issuer and provider-account identity.
* [`backup-table-conflict`](/docs/guides/1-7-upgrade-guide#backup-table-conflict) - The `__better_auth_1_6` backup name is taken or holds an unexpected layout.
* [`identifier-length-limit`](/docs/guides/1-7-upgrade-guide#identifier-length-limit) - A generated backup table name exceeds the portable identifier limit.
* [`issuer-conflict`](/docs/guides/1-7-upgrade-guide#issuer-conflict) - A recorded issuer contradicts the one the configuration derives.
* [`issuer-required`](/docs/guides/1-7-upgrade-guide#issuer-required) - A provider in the account data has no issuer the configuration can derive.
* [`legacy-table-candidate`](/docs/guides/1-7-upgrade-guide#legacy-table-candidate) - A table holds a retired model's 1.6 columns under a name no configuration declares.
* [`oauth-client-conflict`](/docs/guides/1-7-upgrade-guide#oauth-client-conflict) - A 1.6 client has no redirect URI or collides with an existing 1.7 client.
* [`oauth-client-decision-required`](/docs/guides/1-7-upgrade-guide#oauth-client-decision-required) - Registered 1.6 clients exist and no OAuth decision was recorded.
* [`oauth-consent-conflict`](/docs/guides/1-7-upgrade-guide#oauth-consent-conflict) - A 1.7 consent already exists with different scopes.
* [`oauth-consent-decision-required`](/docs/guides/1-7-upgrade-guide#oauth-consent-decision-required) - Stored consents need a `migrate` or `reauthorize` decision.
* [`oauth-token-decision-required`](/docs/guides/1-7-upgrade-guide#oauth-token-decision-required) - Retiring the 1.6 provider tokens has not been acknowledged.
* [`release-migration-error`](/docs/guides/1-7-upgrade-guide#release-migration-error) - The 1.6 preflight could not finish; the message comes from the migration engine.
* [`reprovision-data`](/docs/guides/1-7-upgrade-guide#reprovision-data) - The old and new models have different lifecycle semantics and require a new provisioning cycle.
* [`required-column-backfill`](/docs/guides/1-7-upgrade-guide#required-column-backfill) - Existing rows need values for new required columns.
* [`required-column-constraint`](/docs/guides/1-7-upgrade-guide#required-column-constraint) - Backfilled columns must be made non-nullable.
* [`retired-table-data`](/docs/guides/1-7-upgrade-guide#retired-table-data) - Rows from a retired model must be removed before its replacement is created.
* [`scim-decision-required`](/docs/guides/1-7-upgrade-guide#scim-decision-required) - Legacy SCIM data exists and no retirement inventory was confirmed.
* [`scim-inventory-mismatch`](/docs/guides/1-7-upgrade-guide#scim-inventory-mismatch) - The retirement inventory does not match the accounts the legacy providers own.
* [`table-data-conversion`](/docs/guides/1-7-upgrade-guide#table-data-conversion) - A retained model has data whose physical encoding changed.
* [`table-data-move`](/docs/guides/1-7-upgrade-guide#table-data-move) - Rows must move from a retired model to its replacement.

<Callout type="info">
  **Using PostgreSQL with a non-default schema?**

  The migrate command automatically detects your configured `search_path` and creates tables in the correct schema. See the [PostgreSQL adapter documentation](/docs/adapters/postgresql#use-a-non-default-schema) for configuration details.
</Callout>

## Create Admin

The `create-admin` command creates an initial admin user through your configured Better Auth instance. It requires the Admin plugin and a persistent database, and it uses the same server-side `auth.api.createUser` path as the Admin plugin so passwords are hashed and database hooks still run.

```package-install title="Terminal"
npx auth@latest create-admin --email admin@example.com --name "Admin" --role admin
```

If users already exist, the command asks for confirmation. Use `--force` or `--yes` to skip that prompt.

### Options

* `--email` - The email address for the admin user.
* `--password` - The password for the admin user. If omitted, the CLI will prompt for it.
* `--name` - The name for the admin user. Defaults to `Admin`.
* `--role` - The role to assign. Defaults to `admin`.
* `--data` - Additional user fields as a JSON object.
* `--no-email-verified` - Create the admin user with an unverified email. By default, the CLI marks the admin email as verified.
* `--config` - The path to your Better Auth config file.
* `--force` - Create the admin user even when users already exist.
* `--yes` - Skip the existing-users confirmation prompt.

## Init

The `init` command allows you to initialize Better Auth in your project.

```package-install title="Terminal"
npx auth@latest init
```

### Options

* `--name` - The name of your application. (defaults to the `name` property in your `package.json`).
* `--framework` - The framework your codebase is using. Currently, the only supported framework is `Next.js`.
* `--plugins` - The plugins you want to use. You can specify multiple plugins by separating them with a comma.
* `--database` - The database you want to use. Currently, the only supported database is `SQLite`.
* `--package-manager` - The package manager you want to use. Currently, the only supported package managers are `npm`, `pnpm`, `yarn`, `bun` (defaults to the manager you used to initialize the CLI).

## Info

The `info` command provides diagnostic information about your Better Auth setup and environment. Useful for debugging and sharing when seeking support.

```package-install title="Terminal"
npx auth@latest info
```

### Output

The command displays:

* **System**: OS, CPU, memory, Node.js version
* **Package Manager**: Detected manager and version
* **Better Auth**: Version and configuration (sensitive data auto-redacted)
* **Frameworks**: Detected frameworks (Next.js, React, Vue, etc.)
* **Databases**: Database clients and ORMs (Prisma, Drizzle, etc.)

### Options

* `--config` - Path to your Better Auth config file
* `--json` - Output as JSON for sharing or programmatic use

### Examples

```bash
# Basic usage
npx auth@latest info

# Custom config path
npx auth@latest info --config ./config/auth.ts

# JSON output
npx auth@latest info --json > auth-info.json
```

Sensitive data like secrets, API keys, and database URLs are automatically replaced with `[REDACTED]` for safe sharing.

## Secret

The CLI also provides a way to generate a secret key for your Better Auth instance.

```package-install title="Terminal"
npx auth@latest secret
```

## Common Issues

**Error: Cannot find module X**

The CLI resolves most imports for you: `tsconfig.json` path aliases (including SvelteKit's `$lib`) and stubbed framework virtual modules (`$env/*`, `$app/*`, `cloudflare:workers`, Vite assets like `?raw`). For SvelteKit, run `svelte-kit sync` first so `.svelte-kit/tsconfig.json` exists.

A few module types can't load outside their bundler (e.g. `.svelte` components or `import.meta.glob`). Keep those out of your config file's import graph.
