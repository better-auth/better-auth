Better Auth rate limits client-initiated requests in production by default. The default policy allows 100 requests per 10-second fixed window. Sensitive authentication endpoints and plugins can apply stricter policies.

<Callout type="warning">
  Calls made directly through `auth.api` do not pass through request rate limiting.
</Callout>

Enable rate limiting explicitly in development or test environments:

```ts title="auth.ts"
import { betterAuth } from "better-auth";

export const auth = betterAuth({
  rateLimit: {
    enabled: true,
  },
});
```

## Policies

A policy defines how a budget is consumed. Better Auth supports four strategies:

```ts title="auth.ts"
import { betterAuth } from "better-auth";

export const auth = betterAuth({
  rateLimit: {
    policy: {
      strategy: "fixed-window",
      limit: 100,
      windowMs: 10_000,
    },
  },
});
```

* `fixedWindow`: Starts a window on the first accepted request and resets the complete budget at its deadline.
* `slidingWindowCounter`: Approximates a rolling window by weighting the previous and current time buckets.
* `tokenBucket`: Refills capacity continuously and allows bursts up to the configured capacity.
* `gcra`: Enforces a steady emission rate with compact state and configurable burst capacity.

Examples:

```ts
const slidingWindowCounter = {
  strategy: "sliding-window-counter",
  limit: 100,
  windowMs: 60_000,
};

const tokenBucket = {
  strategy: "token-bucket",
  capacity: 20,
  refillRate: 5,
  refillIntervalMs: 1_000,
};

const gcra = {
  strategy: "gcra",
  limit: 10,
  windowMs: 1_000,
  burst: 20,
};
```

## Endpoint rules

Use `rules` to override the default or plugin policy for an exact path or wildcard. A rule can also disable request rate limiting for that scope.

```ts title="auth.ts"
import { betterAuth } from "better-auth";

export const auth = betterAuth({
  rateLimit: {
    policy: {
      strategy: "token-bucket",
      capacity: 100,
      refillRate: 10,
      refillIntervalMs: 1_000,
    },
    rules: {
      "/sign-in/*": {
        strategy: "fixed-window",
        limit: 3,
        windowMs: 10_000,
      },
      "/get-session": false,
      "/organization/*": async (request, currentPolicy) => {
        return request.headers.has("x-internal-request")
          ? false
          : currentPolicy;
      },
    },
  },
});
```

Application rules run after built-in and plugin rules, so they are the final policy override.

## Consumer keys

By default, each normalized endpoint path has a separate budget for each trusted client IP. The path is the budget scope; the IP is the consumer key.

Use `key` when your application needs another stable identity, such as a verified tenant, API client, or user identifier. Return a compact, non-secret value:

```ts title="auth.ts"
export const auth = betterAuth({
  rateLimit: {
    key: async ({ request, ip }) => {
      const principal = await verifyApplicationToken(request.headers);
      return principal?.tenantId ?? ip ?? "anonymous";
    },
  },
});
```

<Callout type="warning">
  Only derive keys from trusted data. An unsigned user or tenant header lets clients choose a new budget and bypass the limit.
</Callout>

The request limiter runs before endpoint authentication. If a budget depends on an authenticated session produced inside a handler, enforce it after authentication in your application.

### Connecting IP address

Point `ipAddressHeaders` at a single header that your infrastructure overwrites:

```ts title="auth.ts"
export const auth = betterAuth({
  advanced: {
    ipAddress: {
      ipAddressHeaders: ["cf-connecting-ip"],
    },
  },
});
```

Better Auth does not trust comma-separated forwarded chains unless you configure `trustedProxies`. It walks a trusted chain from right to left and selects the first untrusted address:

```ts title="auth.ts"
export const auth = betterAuth({
  advanced: {
    ipAddress: {
      trustedProxies: ["192.0.2.10", "10.0.0.0/24"],
    },
  },
});
```

<Callout type="warning">
  Keep the origin reachable only through the configured proxies, and make every proxy overwrite or sanitize forwarded IP headers.
</Callout>

Better Auth normalizes equivalent IPv6 representations and IPv4-mapped IPv6 addresses. IPv6 addresses use a `/64` subnet by default to prevent address rotation within one allocation. Change it with `advanced.ipAddress.ipv6Subnet` when your network uses another allocation boundary.

## Storage

Every storage backend exposes one atomic `consume` operation. The policy evaluation and state update cannot be split into separate `get` and `set` calls, because concurrent requests could otherwise consume the same stale budget.

### Memory

Memory storage is the default. It is bounded and fast, but each process has independent budgets. Use it for a single process or when approximate per-instance enforcement is acceptable.

### Database

Use database storage for shared, durable enforcement:

```ts title="auth.ts"
export const auth = betterAuth({
  rateLimit: {
    storage: "database",
    modelName: "rateLimit",
  },
});
```

Run `npx auth@latest migrate` with the built-in Kysely adapter. For Prisma, Drizzle, or another ORM, run `npx auth@latest generate` and apply the generated migration.

Database storage uses compare-and-swap revisions, so concurrent requests are evaluated against the latest committed state.

### Custom atomic storage

Use `customStorage` to integrate Redis, a durable object, or another store that can perform an atomic transition:

```ts title="auth.ts"
import { betterAuth } from "better-auth";

export const auth = betterAuth({
  rateLimit: {
    customStorage: {
      async consume(key, policy, options) {
        // Evaluate and persist this transition in one transaction, Lua script,
        // compare-and-swap loop, or equivalent atomic operation.
        return consumeAtomically(key, policy, options);
      },
    },
  },
});
```

Secondary storage is not selected implicitly for rate limiting because its generic `get` and `set` contract cannot guarantee atomic enforcement. A provider can expose a dedicated `RateLimitStorage` implementation instead.

## Handling errors

An exhausted budget returns HTTP `429` and a standard `Retry-After` header containing the number of seconds until the next request can be accepted.

```ts title="auth-client.ts"
import { createAuthClient } from "better-auth/client";

export const authClient = createAuthClient({
  fetchOptions: {
    onError(context) {
      if (context.response.status === 429) {
        const retryAfter = context.response.headers.get("Retry-After");
        console.log(`Retry after ${retryAfter} seconds`);
      }
    },
  },
});
```
