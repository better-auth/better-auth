The OAuth Provider plugin turns your Better Auth server into an authorization server that implements [OAuth 2.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1), [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html), and [RFC 8414](https://datatracker.ietf.org/doc/html/rfc8414) metadata. Other applications send users to your app to sign in and receive access tokens for your APIs.

The defaults follow the safer protocol choice: S256 PKCE, exact redirect URI matching, the `iss` authorization response parameter, and tokens bound to the resources each client is linked to.

<Callout type="info">
  To sign users in to your app with another provider, use [social providers](/docs/concepts/oauth), [Generic OAuth](/docs/plugins/generic-oauth), or [SSO](/docs/plugins/sso) instead.
</Callout>

## Features

* [Authorization code grant](/docs/plugins/oauth-provider/sign-in-flow#how-the-redirect-works) with S256 PKCE, login, consent, and account selection screens
* [Refresh tokens](/docs/plugins/oauth-provider/tokens#refresh-tokens) through the `offline_access` scope
* [Client credentials](/docs/plugins/oauth-provider/clients#client-credentials-scopes) for machine-to-machine access
* [Device code grant](/docs/plugins/device-authorization) for CLIs and limited-input devices
* [Dynamic client registration](/docs/plugins/oauth-provider/clients#dynamic-client-registration) and [Client ID Metadata Documents](/docs/plugins/cimd)
* [`private_key_jwt`](/docs/plugins/oauth-provider/clients#private-key-jwt) client authentication
* [DPoP](/docs/plugins/oauth-provider/tokens#dpop) sender-constrained access tokens
* [OpenID Connect](/docs/plugins/oauth-provider/openid-connect) ID tokens, UserInfo, and [logout](/docs/plugins/oauth-provider/openid-connect#rp-initiated-logout)

## Installation

<Steps>
  <Step>
    ### Install the plugin

    ```package-install
    @better-auth/oauth-provider
    ```
  </Step>

  <Step>
    ### Add the plugin to the server

    The provider signs tokens with the [JWT plugin](/docs/plugins/jwt). Disable the JWT plugin's `/token` route, because `/oauth2/token` is the token endpoint clients call.

    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { jwt } from "better-auth/plugins";
    import { oauthProvider } from "@better-auth/oauth-provider"; // [!code highlight]

    export const auth = betterAuth({
      disabledPaths: ["/token"], // [!code highlight]
      plugins: [
        jwt(),
        oauthProvider({ // [!code highlight]
          loginPage: "/sign-in", // [!code highlight]
          consentPage: "/consent", // [!code highlight]
        }), // [!code highlight]
      ],
    });
    ```

    <Callout type="warn">
      With [secondary storage](/docs/concepts/database#secondary-storage), also set `session.storeSessionInDatabase: true`. The provider looks sessions up in the database and fails at startup without it.
    </Callout>
  </Step>

  <Step>
    ### Migrate the database

    Run the migration or generate the schema to add the necessary fields and tables to the database.

    <Tabs items={["migrate", "generate"]}>
      <Tab value="migrate">
        ```package-install
        npx auth migrate
        ```
      </Tab>

      <Tab value="generate">
        ```package-install
        npx auth generate
        ```
      </Tab>
    </Tabs>

    See the [Schema](/docs/plugins/oauth-provider/reference#schema) section to add the fields manually.
  </Step>

  <Step>
    ### Expose the well-known metadata

    The auth handler serves these routes. If your framework forwards only a catch-all auth route to `auth.handler`, add routes for the ones it misses.

    | Metadata                                                                                              | Path                                                                                                          | Helper                              |
    | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
    | [RFC 8414](https://datatracker.ietf.org/doc/html/rfc8414#section-3) authorization server              | `{issuer}/.well-known/oauth-authorization-server` and `/.well-known/oauth-authorization-server/{issuer-path}` | `oauthProviderAuthServerMetadata`   |
    | [OpenID Connect Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfig) | `{issuer}/.well-known/openid-configuration`                                                                   | `oauthProviderOpenIdConfigMetadata` |

    The OpenID configuration is served only when `scopes` includes `openid`, which it does by default. Without a custom issuer, the issuer path is your `basePath`, such as `/api/auth`.

    ```ts title="app/.well-known/oauth-authorization-server/api/auth/route.ts"
    import { oauthProviderAuthServerMetadata } from "@better-auth/oauth-provider";
    import { auth } from "@/lib/auth";

    export const GET = oauthProviderAuthServerMetadata(auth);
    ```

    <Callout type="info">
      A browser-based client that fetches metadata from another origin needs CORS on these routes. For local testing, allow `GET` from any origin.
    </Callout>
  </Step>

  <Step>
    ### Add the client plugins

    Add `oauthProviderClient` to the app that renders your login and consent pages. It forwards the signed authorization request to the endpoints that need it.

    ```ts title="auth-client.ts"
    import { createAuthClient } from "better-auth/client";
    import { oauthProviderClient } from "@better-auth/oauth-provider/client"; // [!code highlight]

    export const authClient = createAuthClient({
      plugins: [oauthProviderClient()], // [!code highlight]
    });
    ```

    Add `oauthProviderResourceClient` to an API that verifies access tokens. Pass `auth` when the API runs in the same process as the provider. See [Protect your API](/docs/plugins/oauth-provider/resource-server#verify-access-tokens) for the verification options to set.

    ```ts title="server-client.ts"
    import { createAuthClient } from "better-auth/client";
    import { oauthProviderResourceClient } from "@better-auth/oauth-provider/resource-client"; // [!code highlight]
    import { auth } from "@/lib/auth";

    export const serverClient = createAuthClient({
      plugins: [oauthProviderResourceClient(auth)], // [!code highlight]
    });
    ```
  </Step>
</Steps>

## Login and consent pages

The authorize endpoint redirects to `loginPage` when the user has no session, and to `consentPage` when the client needs the user's approval. Both receive a signed copy of the authorization request.

Your login page signs the user in as usual, and the plugin continues the flow when the session is created. Your consent page calls `authClient.oauth2.consent`. See [Sign-in and consent screens](/docs/plugins/oauth-provider/sign-in-flow) to build both.

## Run your first flow

This flow issues an access token for one API, `https://api.example.com`.

<Steps>
  <Step>
    ### Register the API and a client

    Add the API to `resources`, then create a client linked to it. `adminCreateOAuthClient` runs only on the server and needs a signed-in user's session, so pass the headers of that user's request.

    ```ts title="auth.ts"
    oauthProvider({
      loginPage: "/sign-in",
      consentPage: "/consent",
      resources: ["https://api.example.com"], // [!code highlight]
    })
    ```

    ```ts title="create-client.ts"
    const client = await auth.api.adminCreateOAuthClient({
      headers: request.headers,
      body: {
        client_name: "Example App",
        redirect_uris: ["https://app.example.com/callback"],
        resources: ["https://api.example.com"],
      },
    });
    // Store client.client_id and client.client_secret in the client app.
    ```

    For a public client, such as a single-page or native app, add `token_endpoint_auth_method: "none"`. It gets no secret and authenticates with PKCE alone.
  </Step>

  <Step>
    ### Send the user to the authorize endpoint

    The client app generates a PKCE verifier, then redirects with its S256 challenge as described in [RFC 7636 §4.2](https://datatracker.ietf.org/doc/html/rfc7636#section-4.2).

    ```txt
    https://auth.example.com/api/auth/oauth2/authorize
      ?response_type=code
      &client_id=CLIENT_ID
      &redirect_uri=https://app.example.com/callback
      &scope=openid profile offline_access
      &state=STATE
      &code_challenge=CODE_CHALLENGE
      &code_challenge_method=S256
      &resource=https://api.example.com
    ```
  </Step>

  <Step>
    ### Sign in and consent

    The user signs in on `loginPage` and approves on `consentPage`. The provider then redirects to `redirect_uri` with `code`, `state`, and `iss`.
  </Step>

  <Step>
    ### Exchange the code for tokens

    The client app posts the code and the PKCE verifier to the token endpoint.

    ```bash
    curl -X POST https://auth.example.com/api/auth/oauth2/token \
      -u "CLIENT_ID:CLIENT_SECRET" \
      -d grant_type=authorization_code \
      -d code=CODE \
      -d redirect_uri=https://app.example.com/callback \
      -d code_verifier=CODE_VERIFIER \
      -d resource=https://api.example.com
    ```

    The response holds an access token for `https://api.example.com`, an ID token, and a refresh token.
  </Step>
</Steps>

<Callout type="warn">
  `enforcePerClientResources` defaults to `true`, so the authorize and token endpoints reject a `resource` that is not linked to the client. Link resources when you create the client, or see [Resources](/docs/plugins/oauth-provider/tokens#resources).
</Callout>
