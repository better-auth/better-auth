Every SSO sign-in ends with a Better Auth user. This page covers how that user is found or created, how to run your own code on sign-in, and how users join organizations.

## How SSO users are matched

Better Auth stores each SSO identity as an `account` keyed by the provider ID and the OIDC `sub` claim or the SAML `NameID`. Only that pair identifies the person, not the email ([OIDC Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability), [SAML Core §2.2.3](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)).

* **Returning account.** The user who owns the account signs in.
* **New account, no user with that email.** A new user is created with `emailVerified: false`.
* **New account, a user with that email exists.** The account is linked to that user only when the provider's [domain is verified](/docs/plugins/sso/domain-verification#domain-verification) and the email's domain is one of the provider's domains, or when [`resolveUser`](#resolve-sso-users) returns `link`. Domain-based linking also needs the existing user's email to be verified and `account.accountLinking` not to be disabled. Otherwise the sign-in fails: OIDC redirects with `error=account not linked`, and SAML with `error=account_not_linked`.

`account.accountLinking.trustedProviders` does not apply to SSO providers, and registration rejects a `providerId` listed there. SSO provider IDs are chosen by whoever registers them, so trust comes only from a verified domain.

<Callout type="warn">
  The deprecated `trustEmailVerified` option trusts the IdP's `email_verified` claim or mapped attribute. Anyone who can register a provider can then claim any email address and take over its account. Use domain verification or `resolveUser` instead.
</Callout>

### Block new users

With `disableImplicitSignUp: true`, an SSO sign-in that would create a user fails with `error=signup disabled` (SAML: `error=signup_disabled`). An OIDC sign-in can still create one when `signIn.sso` is called with `requestSignUp: true`. SAML ignores `requestSignUp`.

```ts title="auth.ts"
sso({
  disableImplicitSignUp: true, // [!code highlight]
});
```

### Update profiles on sign-in

By default the user's profile is set only when the user is created. With `overrideUserInfo: true` on an OIDC provider, each sign-in overwrites the user's `name`, `email`, `image`, and mapped additional fields with the IdP's values. Pass it in the registration body, or set `defaultOverrideUserInfo: true` on the plugin to apply it to providers registered afterwards. SAML sign-ins update the profile only when `resolveUser` returns `profile: "update"`.

## Resolve SSO Users

Use `resolveUser` when an OIDC or SAML identity must be mapped to an existing Better Auth user instead of relying on email matching. The resolver runs on every SSO sign-in after the protocol identity has been verified.

```ts title="auth.ts"
import { betterAuth } from "better-auth";
import { sso } from "@better-auth/sso";
import {
    findProvisionedUserByAccountKey,
    validateOIDCClaims,
    validateSAMLAttributes,
} from "@/lib/provisioning";

const auth = betterAuth({
    plugins: [
        sso({
            resolveUser: async (input, context) => {
                if (input.providerId !== "workforce") {
                    return { action: "continue" };
                }

                if (input.protocol === "oidc") {
                    await validateOIDCClaims(input.verifiedIdTokenClaims);
                } else {
                    await validateSAMLAttributes(input.providerAttributes);
                }

                const provisionedUser = await findProvisionedUserByAccountKey({
                    providerId: input.providerId,
                    issuer: input.accountKey.issuer,
                    subject: input.accountKey.accountId,
                    database: context.database,
                });

                if (!provisionedUser) {
                    return {
                        action: "reject",
                        code: "PROVISIONED_USER_NOT_FOUND",
                    };
                }

                return {
                    action: "link",
                    userId: provisionedUser.userId,
                    profile: "preserve",
                };
            },
        }),
    ],
});
```

The resolver receives:

| Input                   | OIDC                                                                           | SAML                                                                    |
| ----------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| `accountKey.issuer`     | The ID token's `iss`                                                           | The IdP entity ID                                                       |
| `accountKey.accountId`  | The ID token's `sub`                                                           | The signed `NameID`. Matching is case-sensitive.                        |
| `providerUser`          | The normalized profile                                                         | The normalized profile                                                  |
| `verifiedIdTokenClaims` | The full verified ID token payload                                             | Not present                                                             |
| `providerClaims`        | The UserInfo claims, or the ID token claims when there is no UserInfo endpoint | Not present                                                             |
| `providerAttributes`    | Not present                                                                    | The verified assertion attributes. Multi-valued attributes stay arrays. |
| `providerReference`     | Opaque. Never persist it.                                                      | Opaque. Never persist it.                                               |

Profile fields, claims, and attributes may still need validation before you use them for authorization. `findProvisionedUserByAccountKey` is application-owned in this example. It should resolve the exact provider, issuer, and subject tuple through the transaction-scoped `context.database` adapter. Do not fall back to matching an email address when the exact provisioned subject is absent.

The resolver returns one of three decisions:

* `{ action: "continue" }` continues the normal SSO sign-in behavior.
* `{ action: "link", userId, profile }` links the exact SSO account to that user. Use `profile: "preserve"` to keep the local profile or `profile: "update"` to update it from the provider profile.
* `{ action: "reject", code, message? }` rejects the sign-in with an application-defined error.

<Callout type="warn">
  `resolveUser` requires native database transactions and async-context support, and OIDC sign-ins must return an ID token. With secondary storage, set `session.storeSessionInDatabase: true` and leave `session.preserveSessionInDatabase` off. A fresh sign-in attempt may call the resolver again, so keep it idempotent.
</Callout>

Writes made through `context.database` during resolution, linking, and session creation commit or roll back together. Network calls, other external side effects, and after-commit hooks are not rolled back.

## User provisioning

`provisionUser({ user, userInfo, token, provider })` runs after a new user signs in through SSO. Set `provisionUserOnEveryLogin: true` to run it on every sign-in. It runs before [organization provisioning](#organization-provisioning).

`userInfo` holds the mapped profile, including any `mapping.extraFields`. `token` holds the OIDC tokens and is `undefined` for SAML.

```ts title="auth.ts"
sso({
  provisionUser: async ({ user, userInfo }) => {
    await upsertProfile(user.id, {
      department: userInfo.department, // from mapping.extraFields
    });
  },
});
```

With `provisionUserOnEveryLogin`, make the callback idempotent. An error thrown from it fails the sign-in response, so catch errors from calls the sign-in does not depend on.

## Organization provisioning

Organization provisioning needs the [organization plugin](/docs/plugins/organization). It adds SSO users to organizations as members.

* **Sign-in through a provider with an `organizationId`.** The user joins that organization with `defaultRole` (`"member"` by default), or with the role `getRole({ user, userInfo, token, provider })` returns.
* **Sign-in through a social provider.** The user joins an organization only when domain verification is on, the stored user's email is verified, and the email's domain matches the verified providers of exactly one organization.

Nothing happens when the user is already a member or has a pending, unexpired invitation to that organization. Automatic provisioning neither accepts nor cancels the invitation. Set `organizationProvisioning.disabled: true` to turn provisioning off.

In `getRole`, `userInfo` is the mapped profile for OIDC, the raw assertion attributes for SAML, and empty for assignment by domain.

```ts title="auth.ts"
sso({
  organizationProvisioning: {
    defaultRole: "member",
    getRole: async ({ userInfo }) => {
      const groups = [userInfo.groups].flat();
      return groups.includes("sso-admins") ? "admin" : "member";
    },
  },
});
```

## Link a provider to an organization

Pass `organizationId` when you register a provider. Users who sign in through it join that organization.

```ts title="register-provider.ts"
await auth.api.registerSSOProvider({
  body: {
    providerId: "acme",
    issuer: "https://idp.acme.com",
    domain: "acme.com",
    organizationId: "org_acme", // [!code highlight]
    samlConfig: { /* ... */ },
  },
  headers: request.headers,
});
```

The caller must be a member of the organization. With the organization plugin, the caller must also be an organization `owner` or `admin`, or the call returns `403`. Owners and admins can then list, update, and delete the provider. Without the plugin, only membership is checked, and only the user who registered the provider can manage it.
