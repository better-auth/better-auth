The ACS endpoint, `{baseURL}/sso/saml2/sp/acs/{providerId}`, runs these checks on every SAML response before it signs anyone in:

1. **Size limit**: the encoded response must fit within `maxResponseSize`.
2. **One assertion**: the response must contain exactly one assertion.
3. **Signature**: the response or assertion signature must verify against the IdP certificate. When the provider sets `wantAssertionsSigned`, the assertion must carry its own signature as well ([Metadata §2.4.4](https://docs.oasis-open.org/security/saml/v2.0/saml-metadata-2.0-os.pdf)).
4. **Algorithms**: the signature and encryption algorithms must be allowed.
5. **Timestamps**: the current time must fall between `NotBefore` and `NotOnOrAfter`.
6. **Audience, recipient, and destination**: the response must be addressed to this service provider and its ACS URL ([Profiles §4.1.4.2](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf)).
7. **InResponseTo**: the response must answer an AuthnRequest this server sent, unless IdP-initiated SSO is allowed or `enableInResponseToValidation` is `false`.
8. **Replay**: the assertion ID must not have been used before.

A failed check redirects to the [error URL](/docs/plugins/sso/saml#acs-and-callback-urls) with `error` set to the lowercased error code (`saml_error` when the error has none) and `error_description` set to the message. Every option sits under `saml` in the plugin options and is listed in the [reference](/docs/plugins/sso/reference#saml).

## InResponseTo validation

InResponseTo validation is on by default. Each AuthnRequest ID is stored as a verification value for `requestTTL` (5 minutes by default), and the matching response consumes it once ([SAML Core §3.2.2](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)). Verification values use secondary storage when it is configured and the database otherwise, so validation works across multiple instances. Replay protection always needs the database; see [Assertion replay protection](#assertion-replay-protection).

A response without `InResponseTo` is IdP-initiated, and it is rejected unless you enable [IdP-initiated SSO](/docs/plugins/sso/saml#idp-initiated-sso). Setting `enableInResponseToValidation: false` turns correlation off for every SAML provider: unsolicited responses are then accepted even when `allowIdpInitiated` is `false`, and the provider-mismatch check is skipped. To accept IdP-initiated sign-in, keep validation on and set `allowIdpInitiated: true` instead.

To give users more time at the IdP login page, raise `requestTTL`:

```ts title="auth.ts"
sso({
  saml: {
    requestTTL: 10 * 60 * 1000, // [!code highlight]
  },
})
```

| `error`                 | `error_description`                         |
| ----------------------- | ------------------------------------------- |
| `invalid_saml_response` | `Unknown or expired request ID`             |
| `invalid_saml_response` | `Provider mismatch`                         |
| `unsolicited_response`  | `IdP-initiated SSO not allowed`             |
| `invalid_state`         | `SSO provider reference missing or invalid` |

## Assertion replay protection

Replay protection is always on for assertions that carry an ID. Each assertion ID is reserved atomically in the verification store until `NotOnOrAfter` plus `clockSkew`, or for 15 minutes when the assertion has no `NotOnOrAfter`, and a reused ID redirects with `error=replay_detected` ([Profiles §4.1.4.5](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf)). An assertion whose ID cannot be read skips this check, and a warning is logged.

<Callout type="warn">
  The reservation needs database-backed verification storage. With `secondaryStorage` configured, set [`verification.storeInDatabase: true`](/docs/reference/options#verification), or every SAML sign-in fails at this step.
</Callout>

## Timestamp validation

A response is rejected when the current time is before `NotBefore` minus `clockSkew`, or after `NotOnOrAfter` plus `clockSkew`. `clockSkew` defaults to 5 minutes.

[SAML Core §2.5.1](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf) makes these conditions optional, while [SAML2Int](https://kantarainitiative.github.io/SAMLprofiles/saml2int.html) requires them. By default an assertion without timestamps is accepted and a warning is logged. An assertion without `NotOnOrAfter` never expires, and its replay reservation lasts only 15 minutes, so when unsolicited responses are accepted it can be replayed after that. Set `requireTimestamps: true` unless an IdP you rely on omits these conditions. It rejects only assertions with neither condition, not one that carries `NotBefore` alone.

```ts title="auth.ts"
sso({
  saml: {
    clockSkew: 60_000, // [!code highlight]
    requireTimestamps: true, // [!code highlight]
  },
})
```

| `error`      | `error_description`                                    | Cause                                                      |
| ------------ | ------------------------------------------------------ | ---------------------------------------------------------- |
| `saml_error` | `SAML assertion is not yet valid`                      | The current time is before `NotBefore` minus `clockSkew`.  |
| `saml_error` | `SAML assertion has expired`                           | The current time is after `NotOnOrAfter` plus `clockSkew`. |
| `saml_error` | `SAML assertion missing required timestamp conditions` | `requireTimestamps` is on and the assertion has neither.   |

## Algorithm validation

`algorithms.onDeprecated` decides what happens when a deprecated algorithm appears:

* `"warn"` (default): log a warning and continue.
* `"reject"`: fail the request.
* `"allow"`: continue silently.

In production, set `onDeprecated: "reject"` once your IdPs use only the accepted algorithms below.

The ACS checks the response signature algorithm and, for encrypted assertions, the key and data encryption algorithms. Registration and provider updates check the config's `signatureAlgorithm` and `digestAlgorithm`, and a rejected value fails the request with a 400 error.

| Kind            | Accepted                                     | Deprecated |
| --------------- | -------------------------------------------- | ---------- |
| Signature       | RSA and ECDSA with SHA-256, SHA-384, SHA-512 | RSA-SHA1   |
| Digest          | SHA-256, SHA-384, SHA-512                    | SHA-1      |
| Key encryption  | RSA-OAEP                                     | RSA 1.5    |
| Data encryption | AES-CBC, AES-GCM                             | 3DES       |

Without an allowlist, a signature or digest algorithm that is in neither column is rejected with the error code `SAML_UNKNOWN_ALGORITHM`.

To accept only specific algorithms, set `allowedSignatureAlgorithms`, `allowedDigestAlgorithms`, `allowedKeyEncryptionAlgorithms`, or `allowedDataEncryptionAlgorithms` to a list of algorithm URIs. The `SignatureAlgorithm`, `DigestAlgorithm`, `KeyEncryptionAlgorithm`, and `DataEncryptionAlgorithm` constants exported from `@better-auth/sso` hold these URIs.

```ts title="auth.ts"
import { sso, SignatureAlgorithm } from "@better-auth/sso";

sso({
  saml: {
    algorithms: {
      onDeprecated: "reject", // [!code highlight]
      allowedSignatureAlgorithms: [SignatureAlgorithm.RSA_SHA256], // [!code highlight]
    },
  },
})
```

An algorithm outside the list fails with the error code `SAML_ALGORITHM_NOT_ALLOWED`. A rejected deprecated algorithm fails with `SAML_DEPRECATED_ALGORITHM` at the ACS and `SAML_DEPRECATED_CONFIG_ALGORITHM` at registration.

<Callout type="warn">
  An allowlist replaces the deprecation and unknown-algorithm checks for its kind, so a deprecated URI you list is accepted without a warning. The ACS does not check response digest algorithms, so `allowedDigestAlgorithms` and the SHA-1 digest deprecation apply only to the provider config.
</Callout>

## Size limits

`maxResponseSize` caps the SAML response, 256 KB by default. `maxMetadataSize` caps IdP and SP metadata, 100 KB by default, and registration and provider updates enforce it.

To accept IdPs that send large group claims, raise the response limit:

```ts title="auth.ts"
sso({
  saml: {
    maxResponseSize: 512 * 1024, // [!code highlight]
  },
})
```

These limits apply after the request body has been read. To reject oversized bodies before they reach your app, cap the body size at your reverse proxy or load balancer.
