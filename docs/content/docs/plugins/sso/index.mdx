The SSO plugin lets users sign in through identity providers that you or your customers register at runtime, over [OpenID Connect](https://openid.net/specs/openid-connect-core-1_0.html) or [SAML 2.0](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf). Each registered connection is one row in the `ssoProvider` table. You can also [define connections in code](#configure-providers-in-code).

For a fixed set of providers configured in code, use [Generic OAuth](/docs/plugins/generic-oauth) or [social providers](/docs/concepts/oauth). To let other apps sign in with yours, use [OAuth Provider](/docs/plugins/oauth-provider).

<Callout>
  Self-service SSO, where customers configure their own connection through an onboarding link, is available with [Better Auth Infrastructure](https://dash.better-auth.com/sign-in). For other enterprise needs, [contact us for enterprise](/enterprise).
</Callout>

## Features

* [OIDC discovery](/docs/plugins/sso/oidc#oidc-discovery) of provider endpoints
* [`private_key_jwt`](/docs/plugins/sso/oidc#token-endpoint-authentication) token endpoint authentication
* SAML 2.0 [SP-initiated](/docs/plugins/sso/saml#register-a-saml-provider) and [IdP-initiated](/docs/plugins/sso/saml#idp-initiated-sso) sign-in
* [SAML response validation](/docs/plugins/sso/saml-security): signatures, algorithms, timestamps, audience, and replay
* SAML [Single Logout](/docs/plugins/sso/saml#single-logout)
* [User resolution](/docs/plugins/sso/provisioning#resolve-sso-users) and provisioning
* [Organization provisioning](/docs/plugins/sso/provisioning#organization-provisioning)
* DNS [domain verification](/docs/plugins/sso/domain-verification#enable-domain-verification)

  </Step>

  <Step>

    ```ts title="auth.ts"

    ```
  </Step>

  <Step>
    ### Migrate the database

    Run the migration or generate the schema to add the necessary fields and tables to the database.

    <Tabs items={["migrate", "generate"]}>
      <Tab value="migrate">

      </Tab>

      <Tab value="generate">
        ```package-install
        npx auth generate
        ```
      </Tab>
    </Tabs>

    See the [Schema](/docs/plugins/sso/reference#schema) section to add the fields manually.
  </Step>

  <Step>
    ### Add the client plugin

    `ssoClient()` takes the same `domainVerification` and `schema.ssoProvider.additionalFields` options as the server plugin, so the client types match.

    ```ts title="auth-client.ts"
    import { createAuthClient } from "better-auth/client";
    import { ssoClient } from "@better-auth/sso/client"; // [!code highlight]

    export const authClient = createAuthClient({
      plugins: [
        ssoClient(), // [!code highlight]
      ],
    });
    ```
  </Step>
</Steps>

## Register a provider

`authClient.sso.register` (or `auth.api.registerSSOProvider` on the server) calls `POST /sso/register` and creates a provider owned by the signed-in user. It requires `providerId`, `issuer` (a URL), `domain` (a bare email domain, comma-separated for several), and an `oidcConfig`, a `samlConfig`, or both.

`providerId` must be unique. Registration returns 422 when it matches a built-in provider id, a configured social provider, an `account.accountLinking.trustedProviders` entry, or a `defaultSSO` id.

Each user can register up to `providersLimit` providers (default `10`). Set it to `0` to disable registration. By default any signed-in user can register a provider for any domain, and two providers can claim the same domain. Unless customers register their own connections, set `providersLimit` to a function that returns `0` for everyone except your administrators. When users register their own providers, enable [domain verification](/docs/plugins/sso/domain-verification) so a provider cannot sign anyone in until its domain is proven over DNS.

The response includes `redirectURI`, and `domainVerificationToken` when domain verification is enabled.

```ts title="register-provider.ts"
import { authClient } from "@/lib/auth-client";

const { data } = await authClient.sso.register({
  providerId: "acme",
  issuer: "https://idp.example.com",
  domain: "example.com",
  oidcConfig: {
    clientId: "CLIENT_ID",
    clientSecret: "CLIENT_SECRET",
  },
});
// Configure data.redirectURI as the redirect URI at the identity provider.
```

For every field, see [Register an OIDC provider](/docs/plugins/sso/oidc#register-an-oidc-provider) and [Register a SAML provider](/docs/plugins/sso/saml#register-a-saml-provider).

<Callout type="warn">
  Passing `organizationId` requires organization membership. See [Link a provider to an organization](/docs/plugins/sso/provisioning#link-a-provider-to-an-organization).
</Callout>

### Configure providers in code

`defaultSSO` is an array of `{ providerId, domain, oidcConfig?, samlConfig?, privateKey? }` entries that live in your config instead of the database. They are checked before database providers. With `domainVerification.enabled: true`, they count as verified without a DNS check, so a sign-in can link to an existing user at a listed domain when the other [linking conditions](/docs/plugins/sso/provisioning#how-sso-users-are-matched) hold. Without it, an existing user's first SSO sign-in fails instead of linking. List only domains the IdP is authoritative for.

```ts title="auth.ts"
sso({
  defaultSSO: [
    {
      providerId: "acme-saml",
      domain: "example.com",
      samlConfig: {
        issuer: "https://app.example.com",
        entryPoint: "https://idp.example.com/sso",
        idpMetadata: {
          entityID: "https://idp.example.com",
          cert: "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
        },
      },
    },
  ],
})
```

`privateKey` (`{ privateKeyJwk?, privateKeyPem? }`) supplies the key for [`private_key_jwt`](/docs/plugins/sso/oidc#token-endpoint-authentication) without storing it in the database.

## Sign in

```ts title="sign-in.ts"
import { authClient } from "@/lib/auth-client";

await authClient.signIn.sso({
  email: "user@example.com",
  callbackURL: "/dashboard",
});
```

| Identify the provider by | Match                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| `email`                  | The domain part of the address is matched against provider domains.                                    |
| `domain`                 | Matched against provider domains.                                                                      |
| `organizationSlug`       | The provider linked to that organization. Needs the [organization plugin](/docs/plugins/organization). |
| `providerId`             | The provider with that id.                                                                             |

* When `providerId` is given, the provider is looked up by it alone. Otherwise the domain from `domain` or `email` is matched against each provider's comma-separated domains, checking `defaultSSO` entries before the database. `organizationSlug` selects the organization's provider, but a `defaultSSO` entry matching the domain still wins, and an unknown slug falls back to domain matching.
* `loginHint` is sent to OIDC providers as [`login_hint`](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest), and falls back to `email`. SAML ignores it.
* `providerType` picks the protocol when a provider has both configurations; without it, OIDC is used. Requesting a protocol the provider does not have returns 400.
* `additionalParams` adds parameters to the OIDC authorization request. Reserved parameters such as `state`, `client_id`, and `redirect_uri` are rejected, and SAML providers reject it with 400.
* `requestSignUp: true` creates a new user even when `disableImplicitSignUp` is on, and any caller can set it. It applies to OIDC only; SAML ignores it. To refuse users you have not provisioned, see [Block new users](/docs/plugins/sso/provisioning#block-new-users).
* With domain verification enabled, a provider whose domain is not verified returns 401.

<APIMethod path="/sign-in/sso" method="POST">
  ```ts
  type signInSSO = {
      /**
       * Email address whose domain identifies the provider.
       */
      email?: string = "user@example.com"
      /**
       * Slug of the organization whose provider to use.
       */
      organizationSlug?: string = "example-org"
      /**
       * ID of the provider to use.
       */
      providerId?: string = "acme"
      /**
       * Email domain of the provider.
       */
      domain?: string = "example.com"
      /**
       * URL to redirect to after a successful sign-in.
       */
      callbackURL: string = "/dashboard"
      /**
       * URL to redirect to if sign-in fails.
       */
      errorCallbackURL?: string = "/sign-in/error"
      /**
       * URL to redirect to when the user is new.
       */
      newUserCallbackURL?: string = "/welcome"
      /**
       * OIDC scopes to request. Defaults to the provider's scopes, then `["openid", "email", "profile", "offline_access"]`.
       */
      scopes?: string[] = ["openid", "email", "profile", "offline_access"]
      /**
       * Sent to OIDC providers as `login_hint`.
       */
      loginHint?: string = "user@example.com"
      /**
       * Extra OIDC authorization request parameters. Rejected for SAML.
       */
      additionalParams?: Record<string, string>
      /**
       * Create a new user even when `disableImplicitSignUp` is on. OIDC only.
       */
      requestSignUp?: boolean = true
      /**
       * Protocol to use when the provider has both configurations. Defaults to `oidc`.
       */
      providerType?: "oidc" | "saml" = "oidc"
  }
  ```
</APIMethod>

## Manage providers

`authClient.sso.providers()` (`GET /sso/providers`) lists the providers the caller registered without an organization, plus the providers of organizations where the caller is an `owner` or `admin`. `authClient.sso.getProvider({ query: { providerId } })` (`GET /sso/get-provider`) returns one provider. Both return a sanitized configuration: `clientIdLastFour` instead of the client ID, no secrets, and the parsed SAML signing certificates. Update and delete need the same access.

<APIMethod path="/sso/update-provider" method="POST" requireSession>
  ```ts
  type updateSSOProvider = {
      /**
       * ID of the provider to update.
       */
      providerId: string = "acme"
      /**
       * New issuer URL.
       */
      issuer?: string = "https://idp.example.com"
      /**
       * New email domain or comma-separated domains.
       */
      domain?: string = "example.com"
      /**
       * Fields of the OIDC configuration to change.
       */
      oidcConfig?: Partial<OIDCConfig> = { clientSecret: "NEW_CLIENT_SECRET" }
      /**
       * Fields of the SAML configuration to change. Set `idpInitiatedCallbackUrl` to `null` to clear it.
       */
      samlConfig?: Partial<SAMLConfig>
  }
  ```
</APIMethod>

* A supplied `mapping` replaces the whole previous mapping.
* Changing `domain` resets `domainVerified` to `false`.
* Changing an identity field returns 409 while accounts are linked to the provider. The identity fields are:
  * Both: `issuer`
  * OIDC: authorization, token, userinfo, JWKS, and discovery endpoints, and `clientId`
  * SAML: IdP entity ID, IdP SSO URLs, SP entity ID, NameID format, POST ACS URLs, `wantAssertionsSigned`, and `audience`

<APIMethod path="/sso/delete-provider" method="POST" requireSession>
  ```ts
  type deleteSSOProvider = {
      /**
       * ID of the provider to delete.
       */
      providerId: string = "acme"
  }
  ```
</APIMethod>

<Callout type="warn">
  Deleting a provider also deletes every `account` row linked to it.
</Callout>

Use [`guardProviderMutation`](/docs/plugins/sso/reference#plugin-options) to reject provider changes, for example boundary changes while a directory sync is paired. Throw from it to fail the request with 409 `SSO_PROVIDER_MUTATION_REJECTED`. It needs a database adapter with native transactions.

It runs inside the update or delete transaction after the provider row is locked, and receives `action`, the provider, and, on update, `isAuthenticationBoundaryChange`. That flag is `true` for the identity fields above and for SAML signing certificate changes. It is `false` for OIDC client secret and SAML SP private key rotation.
