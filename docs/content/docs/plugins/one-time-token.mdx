The One-Time Token (OTT) plugin provides functionality to generate and verify secure, single-use session tokens. These are commonly used for across domains authentication.

## Installation

<Steps>
  <Step>
    ### Add the plugin to your auth config

    To use the One-Time Token plugin, add it to your auth config.

    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { oneTimeToken } from "better-auth/plugins/one-time-token"; // [!code highlight]

    export const auth = betterAuth({
        plugins: [
          oneTimeToken() // [!code highlight]
        ]
        // ... other auth config
    });
    ```
  </Step>

  <Step>
    ### Add the client plugin

    Next, include the one-time-token client plugin in your authentication client instance.

    ```ts title="auth-client.ts"
    import { createAuthClient } from "better-auth/client"
    import { oneTimeTokenClient } from "better-auth/client/plugins" // [!code highlight]

    export const authClient = createAuthClient({
        plugins: [
            oneTimeTokenClient() // [!code highlight]
        ]
    })
    ```
  </Step>
</Steps>

## Usage

### 1. Generate a Token

Generate a token using `auth.api.generateOneTimeToken` or `authClient.oneTimeToken.generate`

<APIMethod path="/one-time-token/generate" method="GET" requireSession>
  ```ts
  type generateOneTimeToken = {
  }
  ```
</APIMethod>

This will return a `token` that is attached to the current session which can be used to verify the one-time token. By default, the token will expire in 3 minutes.

### 2. Verify the Token

When the user clicks the link or submits the token, use the `auth.api.verifyOneTimeToken` or `authClient.oneTimeToken.verify` method in another API route to validate it.

<APIMethod path="/one-time-token/verify" method="POST">
  ```ts
  type verifyOneTimeToken = {
      /**
       * The token to verify. 
       */
      token: string = "some-token"
  }
  ```
</APIMethod>

This will return the session that was attached to the token.

## Options

These options can be configured when adding the `oneTimeToken` plugin:

* **`disableClientRequest`** (boolean): Optional. If `true`, the token will only be generated on the server side. Default: `false`.
* **`expiresIn`** (number): Optional. The duration for which the token is valid in minutes. Default: `3`.

```ts
oneTimeToken({
    expiresIn: 10 // 10 minutes
})
```

* **`generateToken`**: A custom token generator function that takes `session` object and a `ctx` as parameters.

* **`disableSetSessionCookie`** (boolean): Optional. If `true`, the session cookie is not set when the token is verified. Default: `false`.

  The token is still consumed and the resolved session is still returned in the response body — this option only skips writing the session cookie on the verify response.

  Use it when the request that verifies the token does not come from the browser that will use the session. The most common case is a cross-domain flow where the cookie set on the verifying domain is not reachable from the app the user lands on.

  In that case, establish the session from a server route on the destination domain rather than in the browser. The verify response body is the resolved session, and its `session.token` is the raw session token — not a cookie value. Better Auth normally writes the session as a signed cookie whose signature is derived from the auth instance's `secret`, so the browser cannot turn the response body into a valid session cookie on its own. Have the destination's server route establish the session through Better Auth on the instance that will read it, and return the session cookie from that route's own response.

```ts
oneTimeToken({
    disableSetSessionCookie: true
})
```

* **`storeToken`**: Optional. This option allows you to configure how the token is stored in your database.

  * **`plain`**: The token is stored in plain text. (Default)
  * **`hashed`**: The token is hashed using the default hasher.
  * **`custom-hasher`**: A custom hasher function that takes a token and returns a hashed token.

<Callout type="info">
  Note: It will not affect the token that's sent, it will only affect the token stored in your database.
</Callout>

Examples:

```ts title="No hashing (default)"
oneTimeToken({
    storeToken: "plain"
})
```

```ts title="built-in hasher"
oneTimeToken({
    storeToken: "hashed"
})
```

```ts title="custom hasher"
oneTimeToken({
    storeToken: {
        type: "custom-hasher",
        hash: async (token) => {
            return myCustomHasher(token);
        }
    }
})
```

* **`setOttHeaderOnNewSession`** (boolean): Optional. If `true`, a one-time token is generated and returned in the `set-ott` response header every time a new session is created. Default: `false`.

  This runs as an after-hook on all requests, so it applies to any flow that creates a session — for example a sign-up or a sign-in. The token is produced by the same generation path as the `generate` endpoint, so it also honors `generateToken`, `expiresIn`, and `storeToken`.

  The plugin also adds `set-ott` to `Access-Control-Expose-Headers`. That only un-hides the header from JavaScript once your CORS configuration already permits the request — the plugin never sends `Access-Control-Allow-Origin` itself. A cross-origin reader still needs your own `Access-Control-Allow-Origin` for the calling origin, plus `Access-Control-Allow-Credentials: true` when the request is credentialed.

```ts
oneTimeToken({
    setOttHeaderOnNewSession: true
})
```

  Verification reads the token from the verification value store and then loads the session it points to. So if the destination app runs its own auth instance against its own database, verification fails with `Invalid token` unless that instance shares the verification and session storage with the generating one — or unless the request is forwarded to the instance that generated the token.

  Read the header off the sign-in response, then exchange it for the session on the other domain:

  ```ts title="client.ts"
  const res = await fetch("/api/auth/sign-in/email", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ email, password }),
  });

  const token = res.headers.get("set-ott");

  // Send it to the destination app, which runs the verify step.
  // `credentials: "include"` is required — fetch defaults to "same-origin",
  // so without it the browser neither sends cookies on the request nor
  // stores the session cookie set on the destination's verify response.
  await fetch("https://app.example.com/api/auth/one-time-token/verify", {
      method: "POST",
      credentials: "include", // [!code highlight]
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ token }),
  });
  ```

  The verify endpoint is served under `basePath`, so the URL above uses the default `/api/auth` prefix and the plugin's `/one-time-token/verify` path.

  <Callout type="warn">
    Because this request is cross-origin and credentialed, the destination has to opt in explicitly. Its response needs `Access-Control-Allow-Credentials: true` and an `Access-Control-Allow-Origin` naming the calling origin — `*` is rejected once credentials are included. Sending `content-type: application/json` also triggers a preflight, so the destination's `OPTIONS` handling has to allow the `content-type` header. See [Cross-Domain Setups](/docs/concepts/cookies#safari-itp-and-cross-domain-setups) if the two apps do not share a parent domain.
  </Callout>
