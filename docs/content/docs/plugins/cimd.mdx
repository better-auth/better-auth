`OAuth2` `MCP`

The [Client ID Metadata Document draft-02](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-02) lets an OAuth client identify itself without registering first. The client's `client_id` is the exact HTTPS URL of a metadata document it hosts. Better Auth validates the document and persists the client through the OAuth Provider's canonical registration path. Validation follows draft-02; where [draft-03](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-03) changed a rule, this page cites the draft-03 section it follows.

MCP 2026-07-28 normatively references CIMD draft-00. Use `metadataProfile: "mcp-2026-07-28"` when composing `cimd()` with `mcp()`. This explicit profile adds MCP's required `client_name` and `redirect_uris` fields without imposing those draft-00 restrictions on generic draft-02 clients.

## Installation

<Steps>
  <Step>
    ### Install the plugin

    ```package-install
    @better-auth/cimd
    ```
  </Step>

  <Step>
    ### Add the plugin to the server

    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { jwt } from "better-auth/plugins";
    import { oauthProvider } from "@better-auth/oauth-provider";
    import { cimd } from "@better-auth/cimd";
    import { fetchClientMetadataResource } from "@better-auth/cimd/node";

    export const auth = betterAuth({
      plugins: [
        jwt(),
        oauthProvider({
          loginPage: "/login",
          consentPage: "/consent",
          scopes: ["openid", "profile", "email", "offline_access"],
        }),
        cimd({
          fetchClientMetadataResource,
        }),
      ],
    });
    ```
  </Step>
</Steps>

`fetchClientMetadataResource` is required. Node.js deployments can use the `@better-auth/cimd/node` implementation shown above. It resolves the original hostname once, rejects the request if any DNS result is not public-routable, connects only to the validated addresses on an isolated connection and tries the next one when an address is unreachable, preserves the original Host and TLS certificate identity, and never follows redirects. A metadata URL whose host is a public IP literal, such as `https://[2606:2800:220:1:248:1893:25c8:1946]/client.json`, skips DNS and connects to that address directly. The certificate must then name the IP address, and a non-public literal is rejected. The transport also stops waiting for DNS when the abort signal fires. The system resolver cannot cancel a lookup it has started, so the lookup keeps running until the resolver answers or times out. To bound that work, at most 16 lookups can be outstanding in the process, abandoned ones included. While 16 are outstanding, a fetch to any hostname fails at once. The plugin answers that refusal like a limit of the [metadata fetch governor](#persistence-and-refresh), with HTTP 429 `temporarily_unavailable`, and starts no `minimumFetchInterval` backoff for the client. The refused fetch still counts against the rolling fetch budgets. This transport intentionally supports only `GET` and `HEAD`, which are the methods CIMD uses to retrieve metadata resources.

Bun, Deno, Workers, and other runtimes must provide the equivalent secure transport at their network boundary. The same transport is used for the metadata document and discovery-owned resources such as `jwks_uri`.

The transport must:

* Parse the target as an HTTPS URL before resolving it.
* Resolve the hostname once and reject every RFC 6890 special-use result.
* Connect to that approved address while preserving TLS hostname and certificate verification for the original host.
* Refuse redirects and honor the supplied method, headers, and abort signal.

Do not perform a DNS check and then call `globalThis.fetch`. Standard Fetch exposes neither the connected peer address nor a portable way to pin it, so that pattern re-resolves the hostname and remains vulnerable to DNS rebinding.

## MCP configuration

```ts title="auth.ts"
import { cimd } from "@better-auth/cimd";
import { mcp } from "@better-auth/mcp";
import { fetchClientMetadataResource } from "@better-auth/cimd/node";

plugins: [
  mcp({
    resource: "https://mcp.example.com/mcp",
    scopes: ["mcp:tools"],
  }),
  cimd({
    fetchClientMetadataResource,
    metadataProfile: "mcp-2026-07-28",
  }),
];
```

The MCP profile requires `client_id`, `client_name`, and a non-empty `redirect_uris` array. DCR remains disabled unless the OAuth Provider explicitly enables it.

### Origin-bound fields

`originBoundFields` stops a metadata document from claiming URIs on a domain other than its own. By default, only `post_logout_redirect_uris` must share the `client_id` origin.

The informative URIs `client_uri`, `logo_uri`, `tos_uri`, and `policy_uri` are not origin-bound by default. An application's website is often hosted apart from its metadata document. [CIMD draft-03 §4.4](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-03#section-4.4) forbids an authorization server from requiring `client_uri` to share the origin of the `client_id` or of any redirect URI. If you add `client_uri` to `originBoundFields`, that is your own policy, and it contradicts the draft. Clients whose website is on another origin then fail to register.

Each informative URI must still be a credential-free HTTP(S) URL on a public host, whether or not it is origin-bound.

## Draft-02 validation

Generic CIMD validation follows draft-02:

* `client_id` must equal the requested metadata URL using simple string comparison. Explicit default ports are therefore significant.
* Client Identifier URLs must use HTTPS and cannot contain credentials, fragments, dot segments, special-use literal/known hosts, or omit an explicit path. An explicit root `/` is accepted with a NOT RECOMMENDED warning; query strings produce a SHOULD NOT warning.
* `client_name` and `redirect_uris` are optional for generic clients. Non-redirect grants such as `client_credentials` are valid when enabled by the OAuth Provider.
* The OAuth Provider remains authoritative for supported grants, response types, redirect policy, and authentication capability.
* Declaring `client_credentials` does not grant machine scopes. New discovered clients persist an empty server-owned `clientCredentialsScopes` ceiling and cannot use the grant until an administrator assigns approved scopes. Metadata refresh preserves that ceiling and cannot create, widen, or clear it.
* Better Auth supports `none` and `private_key_jwt` for discovered clients. Inline `jwks` must use the RFC 7517 `{ "keys": [...] }` object shape. EC keys must use P-256, P-384, or P-521; OKP keys must use Ed25519. Bare arrays, symmetric secret methods, secret fields, private JWK material, other curves, and declared algorithms that do not match the key type and curve are rejected.
* `client_uri`, `logo_uri`, `tos_uri`, and `policy_uri` must be credential-free public HTTP(S) URLs. Better Auth does not fetch or render remote logos. `client_name` and these URLs are claims by the client, not proof of its identity. On your consent page, show the `client_id` host, and serve a logo only from a copy you fetched and trust. See [Sign-in and consent screens](/docs/plugins/oauth-provider/sign-in-flow#consent-page).
* `backchannel_logout_uri` and `backchannel_logout_session_required` are rejected because they would authorize an OP-side POST outside the injected GET transport.
* Server-owned fields, including resource links and administrative controls, cannot be supplied by the document.
* Unknown members are ignored and never persisted. Nonstandard camel-case storage aliases and both spellings of client-credentials scope authority are stripped; recognized credential, privilege, and server-control fields remain fatal.

```json title="https://client.example.com/client-metadata.json"
{
  "client_id": "https://client.example.com/client-metadata.json",
  "grant_types": ["client_credentials"],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://client.example.com/jwks.json"
}
```

## Key set origin

By default, a discovered client's `jwks_uri` must be on the origin of its `client_id` URL or on one of your [`trustedOrigins`](/docs/reference/options#trustedorigins). Otherwise Better Auth rejects the client with `jwks_uri must belong to a trusted origin or the Client ID Metadata Document origin`.

Anyone can publish a metadata document, and Better Auth fetches the `jwks_uri` that the document names. That fetch does not go through `isMetadataDocumentUrlAllowed` or `metadataFetchPolicy`. The origin rule is what limits where a document can make your server send requests ([CIMD draft-03 §4.4](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-03#section-4.4), [§10.7](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-03#section-10.7)).

Some clients publish their document on one host and their keys on another. To accept such a client, return `true` from `isCrossOriginJwksUriAllowed` for that client origin and key origin:

```ts title="auth.ts"
cimd({
  fetchClientMetadataResource,
  isCrossOriginJwksUriAllowed: ({ clientId, jwksUri }) =>
    new URL(clientId).origin === "https://client.example.com" &&
    new URL(jwksUri).origin === "https://keys.example.com",
});
```

Match the client origin and the key origin together. A function that allows a key origin for every `client_id` lets any document make your server fetch any URL on that origin.

Do not add the key origin to `trustedOrigins` instead. `trustedOrigins` applies to the whole app, so that origin would also be trusted for redirects and request-origin checks.

Better Auth calls `isCrossOriginJwksUriAllowed` only for a `jwks_uri` that the default rule rejects. It calls it at these points:

* when the document is first registered
* each time the document is refreshed
* when an administrator updates the client, such as setting its `client_credentials_scopes`
* before each client assertion is verified, so keep it fast

Only a resolved `true` allows the key set. `false`, a thrown error, or a rejected promise keeps the rejection with the same error. The other `jwks_uri` checks still run first: HTTPS, no credentials, no fragment, and a public host. The keys are still fetched through `fetchClientMetadataResource`.

## Persistence and refresh

Discovered clients are stored in `oauthClient` with `clientDiscoveryId: "cimd"`. This nullable provenance field prevents an existing managed or DCR client from being taken over merely because its identifier begins with `https://`, including during a fixed-ID registration race. After a process restart, a CIMD-owned record is fetched and refreshed only by the matching discovery. Managed records are returned without invoking CIMD, while a discovery-owned record fails closed if its owner is unavailable or cannot resolve it. Server-owned `clientCredentialsScopes` is never read from the document and is preserved exactly during refresh.

For the fields the document owns, a refresh stores what the current document lists. When the document stops listing one of them, such as `client_name`, `contacts`, `jwks`, `jwks_uri`, `post_logout_redirect_uris`, or `dpop_bound_access_tokens`, the refresh clears the stored value. A key or post-logout redirect URI that the client removes from its document therefore stops working after the next refresh. A field that registration fills with a default gets that default again instead of being cleared: an omitted `token_endpoint_auth_method` becomes `none`, an omitted `grant_types` becomes `authorization_code`, and an omitted `response_types` becomes `code` while the grants include `authorization_code`, and is cleared otherwise.

A refresh keeps some stored values when the document omits them. A stored `subject_type` stays when the document omits it, because changing it would give every user a different `sub` for the client. A document that states another `subject_type` still changes it. Server-owned settings such as `disabled`, `skipConsent`, `enableEndSession`, `requirePKCE`, and `clientCredentialsScopes` are never read from the document, and a refresh keeps them.

Valid documents follow shared-cache semantics. `s-maxage` takes precedence over `max-age` and `Expires`; validators support conditional revalidation. `Cache-Control: no-store`, `private`, and `Vary: *` prevent cache insertion. A `304` is accepted only when the request sent `If-None-Match` or `If-Modified-Since` for an existing validated entry. Modified responses must be exactly `200`.

The metadata fetch governor is independent from HTTP freshness. Fresh-cache hits and concurrent callers joining the same client fetch consume no budget. Every new fetch consumes its concurrency and rolling-window budget when it starts, and excess work is rejected instead of queued. A successful fetch clears its per-client pacing record, so a response that cannot be cached or is immediately stale can be fetched again while origin and global budgets continue to apply. Failed fetches retain the `minimumFetchInterval` backoff. So does a fetched document that a caller fails to save, and the document is also dropped from the cache, so the next request fetches it again. The metadata cache, client pacing records, and origin budget records are each bounded by `maxCacheEntries`. The governor evicts only inactive records; if every record still protects a live interval, rolling window, or fetch, a new client or origin fails closed.

A fetched document that can be cached is cached once it is validated, before it is saved. The caller that started the fetch and every caller that joined it each save it with their own context, and no caller waits for another caller's save. Until one of those saves succeeds, a caller that finds the document in the cache saves it too, so a caller that ends mid-save cannot leave an older stored client in use for the cache lifetime. Saves are not ordered across callers, so when an older save lands after a newer document was saved, the newer document is saved again on its next cache hit. Each of these saves runs `onClientRefreshed` when it updates a stored client. Once one save succeeds, a cache hit for a caller that already has a stored client returns it without writing it.

A caller that joins another caller's fetch waits at most 10 seconds for that fetch. If the fetch has not finished by then, the caller discards it. A fetch that has run for 10 seconds is also discarded when any new fetch starts. This keeps a fetch that never finishes from holding other clients at the concurrency limit or its pacing record from filling the `maxCacheEntries` bound. A discarded fetch neither caches nor saves its document, and its failure is not reported to any caller. The one exception is a fetch discarded after running for 10 seconds that finishes before any newer fetch for that client has started: its document is then the newest available, so it is saved, and cached when its response allows, as if it had not been discarded. Otherwise, the caller that started a discarded fetch resolves the client again when the fetch finishes. A caller that joined it resolves the client again when the fetch finishes or its own 10-second wait ends, whichever comes first. When it resolves again, the caller saves the fresh document that a newer fetch cached. Without one, the caller joins a newer fetch with a new 10-second wait, or starts a new fetch under the same limits. That new fetch fails with `temporarily_unavailable` when no concurrency slot is free, even if the discarded fetch succeeded.

Refresh remains fail closed unless `metadataStaleIfError` applies, as described in the next section. A network or validation failure preserves the previous database and cache state, and a persistence failure preserves the database state and drops the document it failed to save from the cache. Each rejects the current OAuth request. `onClientRefreshed` receives `previousClient`; operators can compare security-sensitive metadata and choose whether to revoke grants, tokens, or consent.

### Transient refresh failures

By default, a failed refresh rejects the request, even when Better Auth has a stored client that it validated earlier. A short outage at the client's metadata host then stops every known client of that host from signing users in. CIMD draft-03 §6.1 says a transient failure, such as a network error or timeout, should not invalidate a client's established trust.

To keep known clients working through short outages, set `metadataStaleIfError`, an option modeled on the stale-if-error extension of RFC 5861 §4:

```ts title="auth.ts"
cimd({
  fetchClientMetadataResource,
  metadataStaleIfError: "6h",
});
```

A failed refresh then serves the stored client when all of these hold:

* The database has a stored client for the `client_id`.
* The refresh failed transiently: the plugin's 5-second fetch timeout fired, the connection failed with one of the codes below, or the server answered with HTTP 500, 502, 503, or 504.
* The stored client's `updatedAt` is no older than `metadataStaleIfError`.
* Since its last successful refresh, no refresh of the document on this instance failed terminally, as described below.

This is an operator trust policy, not HTTP caching. It applies whatever cache directives the document was served with, including `no-store` and `must-revalidate`, because the stored client is an authorization server registration rather than a cached response, and draft-03 §6.1 states its rule about transient failures for that trust.

Better Auth logs a warning with the `client_id` and the failure. It returns the stored client unchanged, and writes nothing to the database or the metadata cache.

A connection failure counts when the transport's error, or an error in its `cause` chain, has one of these codes: `EAI_AGAIN`, `ECONNRESET`, `ECONNREFUSED`, `ETIMEDOUT`, `EHOSTUNREACH`, `ENETUNREACH`, `EPIPE`, `UND_ERR_CONNECT_TIMEOUT`, `UND_ERR_HEADERS_TIMEOUT`, `UND_ERR_BODY_TIMEOUT`, or `UND_ERR_SOCKET`. On a runtime whose `fetch` throws connection failures without an error code, only the 5-second timeout and HTTP 500, 502, 503, and 504 count as transient.

The 5-second timeout counts as transient even when the delay is local. The Node transport resolves host names with `dns.lookup`, which runs on the Node.js thread pool, 4 threads by default and shared with file system and some crypto work, while the transport allows 16 outstanding lookups. A few client IDs on host names whose DNS servers do not answer can occupy every thread, so lookups for other hosts wait in the queue until the timeout fires. Those timeouts count as transient, so a stored client can be served even though its host is up and would have answered, for example with an HTTP 404 for a document its owner removed. The same applies to key fetches. Keep `metadataStaleIfError` short, and consider a larger thread pool through the `UV_THREADPOOL_SIZE` environment variable, which reduces the queuing.

Every other failure still rejects the request with the same error as without the option. A failure is terminal when the document was retrieved and rejected, or when policy refused the fetch:

* Any HTTP 4xx response, including 429, any other HTTP 5xx response, such as 501 or 505, and any redirect.
* A wrong content type, an oversized body, invalid JSON, or a document that fails validation.
* A document that the OAuth provider refuses to save, such as one with a `jwks_uri` on an origin it does not allow. A database error while saving is not one of these: that request fails, but stale serving continues.
* A `client_id` URL that fails validation or that `isMetadataDocumentUrlAllowed` refuses.

A terminal failure also stops this instance from serving the stored client until a refresh succeeds, as draft-03 §6.1 allows. A client's owner who removes the document to revoke the client then does not see it served again when the host later times out. The record is kept in memory: another instance that did not see the failure, or this instance after a restart, can still serve the stored client during a later transient failure. A failure is recorded only for a request whose stored client could otherwise be served, so failures for client IDs without one cannot fill the records. The records are bounded by `maxCacheEntries`. A record older than `metadataStaleIfError` is dropped first, since it can no longer block anything; when a newer one is dropped, this instance stops serving every stored client last validated before then until it is refreshed.

An error that the transport throws, other than the transient ones above, is not terminal, because no document was retrieved. It rejects the request, and the local limits described below no longer serve the stored client on the strength of an earlier transient failure. It does not stop stale serving, so the next transient failure serves the stored client again:

* A host name that does not resolve (`ENOTFOUND`).
* A refusal by the transport, such as an address that is not public-routable, even when it arrives after the timeout fired.
* A response that the Node transport cannot use, such as a protocol upgrade or a connection that closes before a response.
* A response body that fails while it is read, without one of the codes above.
* Any other error from the transport, including errors from a custom transport that carry none of the codes above.

Such an error is not served stale either: without an error code, a failed connection and the transport's own refusal of an address throw the same error.

Two refusals are local limits rather than failures of the client's host. They neither count as transient failures nor stop stale serving:

* A `metadataFetchPolicy` limit, which answers `temporarily_unavailable`.
* The Node transport's limit on outstanding DNS lookups, or any transport error with the code `ERR_CIMD_DNS_LOOKUP_LIMIT`, which also answers `temporarily_unavailable`.

When one of them refuses the fetch for a client whose last transient failure was at most 5 minutes ago, the request gets the stored client. Otherwise it gets the same error as without the option.

While Better Auth serves a stored client, it does not see changes to the client's document. If the client's owner changes its redirect URIs or keys, or the domain changes hands, the stored values stay in use until a refresh succeeds or the bound passes. Choose the shortest bound that covers the outages you expect to ride out.

The bound counts from the last successful validation, and a failed refresh does not extend it. An administrator's change to the client through the OAuth client endpoints, including an edit of its `client_credentials_scopes`, also updates `updatedAt`, so it restarts the bound. `metadataRevalidationInterval` sets how often a stored client is refreshed while it is in use, and `metadataStaleIfError` sets how long it can be used once refreshes fail. A client that has had no requests for longer than `metadataStaleIfError` was not refreshed in that time, so the first request during an outage fails for it.

While a client is served this way, Better Auth fetches its document at most once a minute. Requests in between get the stored client without a fetch, so an outage does not use up the origin's fetch budget. The first successful fetch saves the document and ends this mode.

A client that authenticates with `private_key_jwt` and a `jwks_uri` also needs its keys at the token endpoint, and its key host often fails together with its metadata host. Better Auth caches fetched keys in memory for 5 minutes. Without this option, it keeps using cached keys for up to 10 minutes after the last successful fetch when fetching new keys fails. With `metadataStaleIfError`, it keeps using them after those 10 minutes when the key fetch fails transiently, and fetches them again at most once a minute while it does. An assertion that names a key the cached set lacks still fetches them again before it is rejected. The transient failures, the terminal failures, the transport errors that are neither, and the 5-minute rule for the DNS lookup limit are the same as for the document. Three things differ:

* The bound counts from the last successful key fetch, which is kept in memory, instead of the stored client's `updatedAt`. Keys are not stored in the database, so after a restart the keys must be fetched before the client can authenticate.
* Key fetches are outside `metadataFetchPolicy`, so its limits neither refuse them nor let stale keys stand in.
* The last failure of each `jwks_uri` is recorded in each server process, in at most 500 records shared by transient and terminal failures. A terminal failure that stops stale serving holds until a key fetch that started after the failed one succeeds. A failure of a fetch that started before the cached keys were fetched is ignored. When the oldest record is dropped and it is a terminal failure, its cached keys are dropped too.

Keys published inline in the document's `jwks` are stored with the client and are not affected.

## Security boundary

The plugin enforces a five-second timeout with portable `AbortController`/`setTimeout`, a streaming 5 KB metadata-document limit, a streaming 64 KiB discovery-owned JWKS limit, JSON and `application/*+json` media types, and redirect rejection. These application-layer checks complement rather than replace the required network transport's DNS resolution and connection-pinning guarantees.

Loopback Client Identifier URLs are not supported. Tests can route HTTPS `.test` origins to in-process handlers through the injected transport without disabling URL or certificate policy. Native client loopback `redirect_uris` remain governed separately by OAuth redirect validation.

## Explicit discovery composition

```ts title="auth.ts"
oauthProvider({
  extensions: [
    {
      clientDiscovery: createCimdClientDiscovery({
        fetchClientMetadataResource,
        metadataRevalidationInterval: "60m",
      }),
    },
  ],
});
```

`ClientDiscovery.id` is persisted as client provenance. A discovery can also provide the focused `fetchClientMetadataResource` seam used for metadata-owned resources.
