`OAuth2` `OIDC`

[Client-Initiated Backchannel Authentication](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html) is an OpenID Connect flow for **decoupled authentication**: the device that asks for the tokens is not the device where the user signs in. The client starts the request on a back channel, the user approves it on their own phone or laptop, and the client receives tokens once they approve. No redirect happens, and the client never sees or controls the user's authentication.

This is the flow to reach for when the thing requesting access cannot open a browser the user trusts:

* An AI agent acting on a user's behalf that has no browser session of its own.
* A CLI or backend job that needs a real person to approve before it proceeds.
* A call-center system where the agent triggers a login the customer approves on their phone.
* A kiosk, smart device, or terminal that should never collect the user's credentials directly.

The plugin extends [`@better-auth/oauth-provider`](./oauth-provider). It adds the backchannel endpoint, the CIBA grant at the token endpoint, and the approval endpoints your UI calls. It requires `oauth-provider` and `jwt`.

## How the flow works

Four parties take part, and they map directly onto the endpoints below.

1. The **client** (the agent, CLI, or device) calls `POST /oauth2/bc-authorize` with its credentials, the requested scopes, and a hint identifying the user. It gets back an `auth_req_id` and a polling `interval`.
2. Your **server** notifies the user out of band through the `sendNotification` callback, typically with a link to your approval page.
3. The **user** opens that page on their own device and approves or denies the request.
4. The **client** polls `POST /oauth2/token` with the `auth_req_id`. While the request is pending it receives `authorization_pending`; once the user approves, it receives the tokens.

The user's authentication and the client's token request never share a device or a browser, which is what makes the flow safe for clients that cannot be trusted with credentials.

<Callout type="info">
  Two token delivery modes are supported (CIBA §5). In **poll** mode the client polls the token endpoint. In **ping** mode the server also calls the client's registered notification endpoint when the user decides, and the client then polls once. Enable ping with `deliveryModes`; each client registers the mode it uses. Push mode is not supported.
</Callout>

        ciba({ // [!code highlight]
          approvalPage: "/ciba/approve", // [!code highlight]

            const user = await getUser(userId); // [!code highlight]

## Register a client

A client can use the backchannel flow only when it is registered for the CIBA grant type and declares its delivery mode in the `backchannel_token_delivery_mode` metadata (CIBA §4). The client must authenticate, so it needs a `client_secret` or another confidential authentication method.

```ts title="register-client.ts"
const client = await auth.api.adminCreateOAuthClient({
  headers, // an authenticated admin session
  body: {
    client_name: "Scheduling Agent",
    grant_types: ["urn:openid:params:grant-type:ciba"],
    metadata: { backchannel_token_delivery_mode: "poll" },
  },
});
// store client.client_id and client.client_secret for the agent
```

A ping-mode client also registers the endpoint the server calls:

```ts
metadata: {
  backchannel_token_delivery_mode: "ping",
  backchannel_client_notification_endpoint: "https://agent.example.com/ciba",
},
```

The notification endpoint must be an absolute `https` URL on a publicly routable host, with no credentials or fragment. Requests from a client whose endpoint does not meet these rules are rejected.

## The client (agent) side

The client starts a request at the backchannel endpoint, then polls the token endpoint until the user responds. Both calls are form-encoded and authenticate the client; the example uses HTTP Basic.

```ts title="agent.ts"
const basic = btoa(`${clientId}:${clientSecret}`);

// 1. Start the backchannel request.
const start = await fetch("https://auth.example.com/api/auth/oauth2/bc-authorize", {
  method: "POST",
  headers: {
    authorization: `Basic ${basic}`,
    "content-type": "application/x-www-form-urlencoded",
  },
  body: new URLSearchParams({
    scope: "openid profile",
    login_hint: "ada@example.com",
    binding_message: "Code 4821",
  }),
}).then((r) => r.json());
// => { auth_req_id, expires_in, interval }

// 2. Poll the token endpoint until the user decides.
let interval = start.interval;
async function poll() {
  const res = await fetch("https://auth.example.com/api/auth/oauth2/token", {
    method: "POST",
    headers: {
      authorization: `Basic ${basic}`,
      "content-type": "application/x-www-form-urlencoded",
    },
    body: new URLSearchParams({
      grant_type: "urn:openid:params:grant-type:ciba",
      auth_req_id: start.auth_req_id,
    }),
  });
  const body = await res.json();
  if (body.error === "authorization_pending") {
    setTimeout(poll, interval * 1000);
    return;
  }
  if (body.error === "slow_down") {
    interval += 5; // CIBA §11: wait at least 5 more seconds from now on
    setTimeout(poll, interval * 1000);
    return;
  }
  if (body.error) throw new Error(body.error); // access_denied, expired_token, ...
  return body; // { access_token, token_type, expires_in, id_token, ... }
}
```

A ping-mode client sends a `client_notification_token` with the backchannel request. When the user approves or denies, the server POSTs `{ "auth_req_id": "..." }` to the registered endpoint with `Authorization: Bearer <client_notification_token>`, and the client then polls once. The server makes one attempt; if it fails, the client can still poll.

## Approval page

Your approval page reads the `auth_req_id` query parameter, shows the request to the signed-in user, and submits their decision. All three calls require a session, and the session user must be the user the request was created for.

```ts title="approve.tsx"
import { createAuthClient } from "better-auth/client";
import { cibaClient } from "@better-auth/ciba/client";

const authClient = createAuthClient({ plugins: [cibaClient()] });

const { data } = await authClient.ciba.request({
  query: { auth_req_id },
});
// => { client_id, client_name, scope, binding_message, resources, status, expires_at }

// On the user's decision:
await authClient.ciba.approve({ auth_req_id });
// or
await authClient.ciba.deny({ auth_req_id });
```

Show the `binding_message` so the user can match it with what the client displays. Approval records the creation time of the approving session as the ID token's `auth_time`, the same rule the authorization code flow uses.

## Sender-constrained tokens (DPoP)

DPoP, [Demonstrating Proof of Possession](./oauth-provider), binds an access token to a key the client holds. If the client presents a DPoP proof on its token poll, the issued token is bound to its key (`cnf.jkt`) and returned as `token_type: "DPoP"`. No CIBA configuration is needed.

## Endpoints

### `POST /oauth2/bc-authorize`

Starts a backchannel request. Accepts `application/x-www-form-urlencoded` (CIBA §7.1), authenticates the client, and returns `auth_req_id`, `expires_in`, and the polling `interval`.

| Parameter                   | Required  | Description                                                                                                      |
| --------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------- |
| `scope`                     | yes       | Space-delimited scopes. Must include `openid`.                                                                   |
| `login_hint`                | yes       | Identifies the user. By default an email, resolved through `resolveUser`.                                        |
| `binding_message`           | no        | Up to 256 characters of plain text shown on both devices.                                                        |
| `client_notification_token` | ping only | Up to 1024 characters. Sent back as a bearer token on the ping callback.                                         |
| `resource`                  | no        | One or more [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) resource indicators the token is bound to. |
| `requested_expiry`          | no        | Requested lifetime in seconds, capped at `expiresIn`.                                                            |

### `POST /oauth2/token`

The standard token endpoint. With `grant_type` set to `urn:openid:params:grant-type:ciba` and an `auth_req_id`, it returns the tokens once the user approves, or one of the poll errors below. Each `auth_req_id` issues tokens once.

### `GET /ciba/request`

Returns the request for your approval page. Requires the owning user's session.

### `POST /ciba/approve` and `POST /ciba/deny`

Approve or deny a pending request by `auth_req_id`. Both require the owning user's session. Only the first decision applies.

## Error handling

The backchannel endpoint returns the [CIBA §13](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html#auth_error_response) errors `invalid_request`, `invalid_scope`, `invalid_client`, `unauthorized_client`, `invalid_binding_message`, or `unknown_user_id`, plus `invalid_target` for an unknown resource.

The token poll returns one of:

| Error                   | Meaning                                                                       |
| ----------------------- | ----------------------------------------------------------------------------- |
| `authorization_pending` | The user has not responded yet. Keep polling.                                 |
| `slow_down`             | Polling too fast. Wait at least 5 more seconds between polls from now on.     |
| `access_denied`         | The user denied the request.                                                  |
| `expired_token`         | The `auth_req_id` expired before the user decided.                            |
| `invalid_grant`         | The `auth_req_id` is unknown, belongs to another client, or was already used. |

## Schema

The plugin adds one model, `cibaRequest`:

| Field                     | Type      | Description                                                                          |
| ------------------------- | --------- | ------------------------------------------------------------------------------------ |
| `authReqId`               | string    | The `auth_req_id`, hashed like the provider's tokens. The raw value is never stored. |
| `clientId`                | string    | The client that started the request.                                                 |
| `userId`                  | string    | The user being asked to authenticate.                                                |
| `scope`                   | string    | The requested scopes.                                                                |
| `bindingMessage`          | string    | The optional binding message.                                                        |
| `resources`               | string\[] | The optional resource indicators.                                                    |
| `status`                  | string    | `pending`, `approved`, or `denied`. An issued request is deleted.                    |
| `clientNotificationToken` | string    | The ping-mode client's notification token.                                           |
| `authTime`                | date      | Creation time of the approving session, issued as `auth_time`.                       |
| `pollingInterval`         | number    | Minimum time between polls, in milliseconds.                                         |
| `lastPolledAt`            | date      | When the client last polled.                                                         |
| `expiresAt`               | date      | When the request expires.                                                            |
| `createdAt`               | date      | When the request was created.                                                        |

## Security

* **The `auth_req_id` is stored hashed**, using the provider's token storage, so a leaked table cannot be used to poll for tokens.
* **Token issuance is single-use and race-safe.** Polling uses the same state machine as the [device authorization grant](./device-authorization): an approved request is claimed and deleted in one atomic step, so of two concurrent polls only one gets tokens.
* **Clients must authenticate.** The backchannel request and every poll authenticate the client and check that it is registered for the CIBA grant (CIBA §7.1). Public clients cannot use the flow.
* **The ping callback checks the endpoint host and does not follow redirects.** The server only calls a registered `https` endpoint whose host is not a private or reserved address, the same check as `backchannel_logout_uri`. The check does not resolve DNS, so register endpoints you trust and restrict outbound network access where you can.
* **Binding messages are plain text.** A `binding_message` with control characters is rejected. Render it as text in your approval UI.

## Current limitations

* Only `login_hint` is supported; `id_token_hint` and `login_hint_token` are rejected.
* Push delivery, `user_code`, signed authentication requests, `acr_values`, and `authorization_details` ([RFC 9396](https://datatracker.ietf.org/doc/html/rfc9396)) are not supported. `acr_values` is ignored, which matches the voluntary `acr_values` semantics of OIDC.
* Client registration metadata is read from the client's `metadata` and checked when the client starts a request, not when it registers.
