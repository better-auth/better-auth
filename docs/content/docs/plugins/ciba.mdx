`OAuth2` `OIDC`

[Client-Initiated Backchannel Authentication](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html) (CIBA) is an OpenID Connect flow for **decoupled authentication**: the client that wants tokens is not where the user signs in. The client names the user, your server sends that user a link, the user approves on their own phone or laptop, and the client then collects tokens. The client never redirects the user and never sees their credentials.

Use it when the client already knows who it is acting for but cannot show that person a browser:

* An AI agent or backend job that needs a person's approval before it acts for them.
* A call-center or support tool where the operator starts a sign-in the customer approves on their phone.
* A kiosk or terminal that should never collect the user's credentials.

If the client can show a code or a QR code to a person in front of it, use the [device authorization grant](./device-authorization) instead.

The plugin extends [`@better-auth/oauth-provider`](./oauth-provider) and requires `oauthProvider()` and `jwt()`. It supports the CIBA poll and ping delivery modes.

## How the flow works

1. The **client** calls `POST /oauth2/bc-authorize` with its credentials, the scopes it wants, and a `login_hint` naming the user. It receives an `auth_req_id` and a polling `interval`.
2. Your **server** reaches the user through your `sendNotification` callback, by email or push notification, with a link to the provider.
3. The **user** opens the link, signs in if needed, and approves or denies on your consent page. They land on your `resultPage`.
4. The **client** polls `POST /oauth2/token` with the `auth_req_id`. It receives `authorization_pending` until the user decides, then the tokens or `access_denied`. A client registered for ping mode is also called back when the user decides, so it can wait for that instead of polling.

## Installation

<Steps>
  <Step>
    ### Install the plugin

    ```package-install
    @better-auth/ciba
    ```
  </Step>

  <Step>
    ### Add the plugin to the server

    Add `ciba()` after `oauthProvider()` and `jwt()`. `sendNotification` sends the user the link, and `resultPage` is the page they land on after deciding. Disable the JWT plugin's `/token` route and its `set-auth-jwt` header, as [OAuth Provider Mode](/docs/plugins/jwt#oauth-provider-mode) describes.

    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { jwt } from "better-auth/plugins";
    import { oauthProvider } from "@better-auth/oauth-provider";
    import { ciba } from "@better-auth/ciba"; // [!code highlight]

    export const auth = betterAuth({
      disabledPaths: ["/token"],
      plugins: [
        jwt({ disableSettingJwtHeader: true }),
        oauthProvider({
          loginPage: "/login",
          consentPage: "/consent",
          scopes: ["openid", "profile", "email"],
        }),
        ciba({ // [!code highlight]
          resultPage: "/ciba", // [!code highlight]
          sendNotification: async ({ user, clientName, bindingMessage, url }) => { // [!code highlight]
            await sendEmail({ // [!code highlight]
              to: user.email, // [!code highlight]
              subject: `${clientName ?? "An application"} wants to act for you`, // [!code highlight]
              text: `${bindingMessage ?? ""}\nReview the request: ${url}`, // [!code highlight]
            }); // [!code highlight]
          }, // [!code highlight]
        }), // [!code highlight]
      ],
    });
    ```
  </Step>

  <Step>
    ### Migrate the database

    The plugin adds a `cibaRequest` model. Run `npx auth@latest migrate` with the built-in Kysely adapter, or run `npx auth@latest generate` and apply the schema with your ORM.
  </Step>

  <Step>
    ### Show the binding message on your consent page

    The link opens your existing `consentPage`. For a CIBA request, its query carries `ciba_request_id`, `client_id`, and `scope`. It also carries what the client sent of `binding_message`, `acr_values`, and `authorization_details`. Show the binding message as plain text next to the client and scopes, so the user can check that it matches what the client displays.

    ```ts title="consent-page.ts"
    const params = new URLSearchParams(location.search);
    const bindingMessage = params.get("binding_message"); // only for CIBA requests
    // A JSON array, only when you configure authorizationDetailsTypes.
    const authorizationDetails = params.get("authorization_details");
    ```

    The client chose the authorization details. Render them as text, never as HTML.

    Accept or deny with `oauth2.consent` as you already do for authorization requests.
  </Step>

  <Step>
    ### Build the result page

    After the user decides, they land on `resultPage` with `status=approved` or `status=denied`. When the link is invalid, expired, already used, or for another account, they land there with `error` and `error_description` instead. Tell them they can return to the app that asked.
  </Step>
</Steps>

## Register a client

A CIBA client is registered for the CIBA grant type and declares its `backchannel_token_delivery_mode` (CIBA §4), and in ping mode its `backchannel_client_notification_endpoint`. Dynamic registration and Client ID Metadata Documents accept both as top-level fields, and admin-created clients put them in `metadata`. Registration rejects a mode not in `deliveryModes`, and a ping endpoint that is not absolute `https` on a public host, with `invalid_client_metadata`.

```ts title="register-client.ts"
import { CIBA_GRANT_TYPE } from "@better-auth/ciba";

const client = await auth.api.adminCreateOAuthClient({
  headers, // an authenticated admin session
  body: {
    client_name: "Support Agent",
    grant_types: [CIBA_GRANT_TYPE], // "urn:openid:params:grant-type:ciba"
    metadata: { backchannel_token_delivery_mode: "poll" },
  },
});
// Store client.client_id and client.client_secret for the agent.
```

The client must authenticate (CIBA §7.1). Agents and CLIs that cannot keep a secret can register with `token_endpoint_auth_method: "none"` when you set `allowPublicClients`; they send `client_id` in the form body of both `/oauth2/bc-authorize` and `/oauth2/token` instead, and should bind their tokens with DPoP.

If anyone can register a client, any client can name any user. Set `resolveUser` to accept only identifiers the requesting client was already given, such as the `sub` from its earlier ID tokens, so a client cannot prompt or look up users it does not know:

```ts title="auth.ts"
ciba({
  resultPage: "/ciba",
  sendNotification,
  resolveUser: async ({ loginHint, client }) => {
    // Your lookup: map the subject this client received back to a user.
    return findUserBySubjectForClient(loginHint, client.clientId);
  },
});
```

## Request tokens from the client

The client starts a request, shows its `binding_message` to whoever is watching, then polls the token endpoint. Both calls are form-encoded and authenticate the client; this example uses HTTP Basic.

```ts title="agent.ts"
const basic = btoa(`${clientId}:${clientSecret}`);
const form = (body: Record<string, string>) => ({
  method: "POST",
  headers: {
    authorization: `Basic ${basic}`,
    "content-type": "application/x-www-form-urlencoded",
  },
  body: new URLSearchParams(body),
});

// 1. Start the request.
const request = await fetch(
  "https://auth.example.com/api/auth/oauth2/bc-authorize",
  form({
    scope: "openid profile",
    login_hint: "ada@example.com",
    binding_message: "Code 4821", // show this in the client too
  }),
).then((r) => r.json());
// => { auth_req_id, expires_in, interval }

// 2. Poll until the user decides.
let interval = request.interval;
for (;;) {
  await new Promise((resolve) => setTimeout(resolve, interval * 1000));
  const body = await fetch(
    "https://auth.example.com/api/auth/oauth2/token",
    form({
      grant_type: "urn:openid:params:grant-type:ciba",
      auth_req_id: request.auth_req_id,
    }),
  ).then((r) => r.json());
  if (body.error === "authorization_pending") continue;
  if (body.error === "slow_down") {
    interval += 5; // CIBA §11: wait at least 5 more seconds from now on
    continue;
  }
  if (body.error) throw new Error(body.error); // access_denied, expired_token, ...
  return body; // { access_token, token_type, expires_in, id_token, ... }
}
```

### Ping mode

Enable ping with `deliveryModes: ["poll", "ping"]`. A ping client registers `backchannel_token_delivery_mode: "ping"` and the `backchannel_client_notification_endpoint` the server calls, and sends a `client_notification_token` with each backchannel request. When the user approves or denies, the server POSTs `{ "auth_req_id": "..." }` to the endpoint registered when the request started with `Authorization: Bearer <client_notification_token>`, and the client then calls the token endpoint once. The server makes one attempt with a 5-second timeout and does not follow redirects. If the callback fails, the client can still poll.

To get a JWT access token for an API, send its [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) `resource` with the request, as with other grants. A DPoP proof on the token poll binds the token to the client's key.

## What the user sees

The link points to `/oauth2/authorize?ciba_request_id=<id>`, so the request runs through the provider's own pages:

1. A signed-out user goes to `loginPage` first. Nothing about the request is shown before sign-in.
2. [`postLogin`](/docs/plugins/oauth-provider/sign-in-flow#post-login-screen) runs as it does for an authorization request, and tokens carry the `referenceId` that `consentReferenceId` returns.
3. `consentPage` always opens, even for a client with `skip_consent` or a stored consent, because the user must confirm each request. The user can narrow the scopes there.
4. The decision is recorded only for the user the `login_hint` named. Anyone else who opens the link, signed in as another account, lands on `resultPage` with an error, and the request stays pending for the right user.

A denial is final: the client's next poll returns `access_denied`, and the link stops working. The ID token's `auth_time` is the creation time of the approving user's session, and its `acr` and `amr` are what the provider's [`authenticationContext.resolve`](/docs/plugins/oauth-provider/openid-connect#authentication-context) returned for that session.

## Request a stronger sign-in

A client can ask for a stronger sign-in with `acr_values`, a space-separated list of ACR values in order of preference (CIBA §7.1). The request is voluntary. The provider accepts values it does not support, and the user can still approve with a weaker sign-in.

* When the user decides from the link, the provider passes the values to [`authenticationContext.resolve`](/docs/plugins/oauth-provider/openid-connect#authentication-context) as `requestedAcrValues`. The ID token's `acr` is what `resolve` returns.
* `sendNotification` receives them as `acrValues`. When your own app collects the decision, authenticate the user as strongly as they ask when you can, and pass the `acr` the user actually proved to `completeCibaRequest`.

The client reads the ID token's `acr` to learn what it got.

## Approve structured actions

Some requests need more than scopes, such as a payment of a stated amount to a stated recipient. A client can describe these actions with `authorization_details` (RFC 9396), a JSON array of objects. Each object has a `type`, and you define the fields of each type.

To accept them, list each type in `authorizationDetailsTypes` with a `validate` function:

```ts title="auth.ts"
import * as z from "zod";

const payment = z.strictObject({
  type: z.literal("payment_initiation"),
  actions: z.array(z.literal("initiate")),
  locations: z.array(z.url()),
  instructedAmount: z.strictObject({ currency: z.string().length(3), amount: z.string() }),
  creditorName: z.string().max(70),
});

ciba({
  resultPage: "/ciba",
  sendNotification,
  authorizationDetailsTypes: {
    payment_initiation: {
      validate: (detail) => payment.safeParse(detail).success,
    },
  },
});
```

Check every field in `validate`, and reject unknown fields and missing required ones. The client chooses every value, and the user approves what your pages show from it.

The provider then handles each request with `authorization_details` as follows:

1. It rejects the request with `invalid_authorization_details` when any of these is true:

   * The value is not a non-empty JSON array of objects.
   * A `type` is not listed in `authorizationDetailsTypes`.
   * A `type` is not among the types the client registered, when it registered any.
   * `validate` returns `false`.

   Without `authorizationDetailsTypes`, every request with `authorization_details` is rejected this way.
2. It shows the details to the user, as `authorizationDetails` in `sendNotification` and as `authorization_details` on the consent page. Approval from the link grants all of them.
3. It returns the granted details as `authorization_details` in the token response. A JWT access token carries them as a claim. For an opaque access token, introspection returns them.

Your API must check `authorization_details` before it acts. For example, it checks that the payment it is asked to make matches the approved amount and recipient.

The granted details belong to the provider. `customAccessTokenClaims` and a resource's `customClaims` cannot replace them in the token or at introspection.

A detail that lists `locations` is issued only in a token for one of those resources. When the poll narrows the token to other resources, that detail is left out of the response and the token (RFC 9396 §9.1). A detail without `locations` goes to every token.

A refreshed or exchanged token would not carry the details. So the provider issues no refresh token when the user approves authorization details, even with `offline_access`, and leaves `offline_access` out of the returned `scope`. Token exchange rejects an access token that carries `authorization_details`.

Discovery metadata lists the types as `authorization_details_types_supported`. Only `/oauth2/bc-authorize` accepts them. So `/oauth2/authorize` and `/oauth2/par` reject a request with `authorization_details` with `invalid_authorization_details`, instead of ignoring the details the client asked for.

To limit a client to some of the types, register it with `authorization_details_types` (RFC 9396 §10), such as `["payment_initiation"]`. Registration fails with `invalid_client_metadata` when a type is not in `authorizationDetailsTypes`. A client without the field may request every listed type.

## Decide from your own app

When your own app can reach the user, such as a mobile app that shows a push notification with Approve and Deny buttons, record the decision from your server with `auth.api.completeCibaRequest` instead of sending the user to the link. `sendNotification` receives the `requestId` to send to the app:

```ts title="auth.ts"
ciba({
  resultPage: "/ciba",
  sendNotification: async ({ requestId, user, clientId, clientName, scopes, bindingMessage }) => {
    // Always show who is asking; not every client has a name.
    await push.send(user.id, { requestId, client: clientName ?? clientId, scopes, bindingMessage });
  },
});
```

When the app reports the user's answer, your server states who decided and how they proved it:

```ts title="push-decision.ts"
await auth.api.completeCibaRequest({
  body: {
    requestId,
    userId: appUser.id, // the user your app authenticated
    decision: approved ? "approved" : "denied",
    // Approval only. Each is optional.
    scopes: ["openid", "profile"], // a subset of the requested scopes
    authTime: new Date(), // issued as auth_time
    acr: "urn:example:acr:biometric", // must be in acrValuesSupported
    amr: ["face"],
    authorizationDetails: approvedDetails, // what the user approved, if the request had any
  },
});
```

The provider records the decision only when `userId` is the user the `login_hint` named and the request is still pending. Otherwise, it returns `invalid_request` and changes nothing. Without `acr`, the ID token claims `"0"`. State an `acr` when `"0"` is not in the provider's [`authenticationContext.acrValuesSupported`](/docs/plugins/oauth-provider/openid-connect#authentication-context). The approved scopes must be among the requested ones and include `openid`. A ping client is called back as it is after a decision from the link.

This call skips the provider's sign-in, post-login, and consent pages. It does not run `postLogin.consentReferenceId`. Tokens issued for a request you decide this way carry no `referenceId`. Your app is responsible for:

* authenticating the user before it reports a decision,
* showing the client, the scopes, and the binding message before the user approves, and
* passing `scopes` without any scope that needs a reference, such as an organization scope.

Without `scopes`, the approval covers every requested scope. Without `authorizationDetails`, it covers every requested detail. Pass `[]` to grant none. Each detail you pass must have a `type` the request carried and pass that type's `validate`. You can change a detail's fields, such as the account the user picked, so pass exactly what the user approved.

The ID token carries only the `auth_time`, `acr`, and `amr` you pass; without `acr` it reports `"0"`.

| Error                           | Meaning                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `invalid_request`               | The request is unknown, already decided, expired, or for another user, or `acr` is not in `acrValuesSupported`.          |
| `invalid_scope`                 | `scopes` includes a scope the client did not request, or leaves out `openid`. The request stays pending.                 |
| `invalid_authorization_details` | A detail in `authorizationDetails` has a type the request did not carry, or fails `validate`. The request stays pending. |

## Endpoints

### `POST /oauth2/bc-authorize`

Starts a request. It accepts only `application/x-www-form-urlencoded` (CIBA §7.1), authenticates the client, and returns `auth_req_id`, `expires_in`, and `interval`. Each IP address can start 10 requests per minute. Discovery metadata advertises it as `backchannel_authentication_endpoint`, with `backchannel_token_delivery_modes_supported` set to `deliveryModes` and `backchannel_user_code_parameter_supported` set to `false`. With `authorizationDetailsTypes`, it also lists `authorization_details_types_supported`.

| Parameter                   | Required  | Description                                                                                                                                            |
| --------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `scope`                     | yes       | Space-delimited scopes. Must include `openid`.                                                                                                         |
| `login_hint`                | yes       | Identifies the user, by email unless you set `resolveUser`.                                                                                            |
| `client_notification_token` | ping only | An RFC 6750 bearer token of at most 1024 characters, sent back on the ping callback.                                                                   |
| `binding_message`           | no        | Up to 64 characters of plain text, in any script, shown in the notification, on the consent page, and by the client.                                   |
| `requested_expiry`          | no        | Requested lifetime in seconds, a positive integer. Capped at `expiresIn`.                                                                              |
| `resource`                  | no        | One or more resource indicators the token is bound to.                                                                                                 |
| `acr_values`                | no        | Space-separated ACR values in order of preference, up to 1024 characters. See [Request a stronger sign-in](#request-a-stronger-sign-in).               |
| `authorization_details`     | no        | A JSON array of RFC 9396 authorization details, up to 4096 characters once URL-encoded. See [Approve structured actions](#approve-structured-actions). |

### `POST /oauth2/token`

The provider's token endpoint. With `grant_type=urn:openid:params:grant-type:ciba` and the `auth_req_id`, it returns the tokens once the user approves, or one of the errors below. Each `auth_req_id` issues tokens once. The poll may send `resource` to narrow the token to some of the approved resources (RFC 8707 §2.2). For a request with authorization details, the response carries the granted `authorization_details`. The poll cannot narrow them: once the user approves, a poll that sends `authorization_details` is rejected with `invalid_authorization_details`.

## Errors

The backchannel endpoint returns these [CIBA §13](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html#auth_error_response) errors:

| Error                           | Meaning                                                                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `invalid_request`               | A required parameter is missing or malformed, the request uses a hint other than `login_hint`, or a ping client sent no valid `client_notification_token`.               |
| `invalid_scope`                 | `scope` does not include `openid`, the client may not request it, or a requested resource does not allow `openid`.                                                       |
| `invalid_client`                | The client did not authenticate, or is public and `allowPublicClients` is off.                                                                                           |
| `unauthorized_client`           | The client is not registered for the CIBA grant with a delivery mode this server supports.                                                                               |
| `invalid_binding_message`       | The binding message is longer than 64 characters or contains control or invisible formatting characters.                                                                 |
| `unknown_user_id`               | No user matches the `login_hint`.                                                                                                                                        |
| `invalid_target`                | A `resource` is malformed or unknown.                                                                                                                                    |
| `invalid_authorization_details` | `authorization_details` is malformed, has a type that is not in `authorizationDetailsTypes`, is not among the client's registered types, or fails its type's `validate`. |

The token poll returns:

| Error                           | Meaning                                                                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `authorization_pending`         | The user has not decided yet. Keep polling.                                                                                   |
| `slow_down`                     | Polling faster than `interval`. Wait at least 5 more seconds between polls.                                                   |
| `access_denied`                 | The user denied the request.                                                                                                  |
| `expired_token`                 | The request expired before the user decided. Once a later request has cleared it, the poll returns `invalid_grant` instead.   |
| `invalid_grant`                 | The `auth_req_id` is unknown, belongs to another client, or was already used.                                                 |
| `invalid_target`                | The poll's `resource` was not approved for this request. The request stays approved.                                          |
| `invalid_scope`                 | The client no longer allows an approved scope, or a requested resource no longer allows `openid`. The request stays approved. |
| `invalid_authorization_details` | The poll sent `authorization_details`. The request stays approved.                                                            |

## Security

* **Only the named user can decide.** Approval from the link always shows consent, so a user who receives a request they did not expect can deny it, and someone else who gets hold of the link cannot approve or deny it. `completeCibaRequest` also refuses a decision for any other user, but it skips consent: it trusts your server to have authenticated that user and shown them the request.
* **Limit who a client can name.** Each request notifies a person, and `unknown_user_id` tells the client whether a hint matched a user, as CIBA §13 specifies. Each IP address can start 10 requests per minute. When anyone can register a client, resolve `login_hint` only to users the client already knows, as shown in [Register a client](#register-a-client).
* **The binding message ties the two devices together.** Ask clients to send a short, random `binding_message` and to display it, so the user can tell their request apart from one someone else started at the same moment. Render it as text.
* **Authorization details come from the client.** The provider checks only their shape and type, and leaves each field to your `validate`. Validate strictly, render them as text, and have your API enforce the granted details itself.
* **The ping callback only reaches safe endpoints.** Registration and each request check that the notification endpoint is absolute `https` on a public host, with no credentials or fragment, the same rules as `backchannel_logout_uri`. The check does not resolve DNS, so restrict outbound network access where you can.
* **Tokens are issued once.** An approved request is claimed and deleted in one atomic step, so of two concurrent polls only one receives tokens. The `auth_req_id` is stored hashed.

## Current limitations

* Push delivery is not supported.
* Only `login_hint` is supported; `id_token_hint` and `login_hint_token` are rejected with `invalid_request`.
* `user_code` and signed authentication requests are not supported.
* Refresh tokens do not store authorization details, so a request with authorization details gets no refresh token, and its access token cannot be exchanged.
* Only `/oauth2/bc-authorize` accepts authorization details.
* There is no API that lists a user's pending requests. To show them in your app, keep the `requestId`s that `sendNotification` receives.
* There is no per-user limit on requests; the limit applies per IP address.
