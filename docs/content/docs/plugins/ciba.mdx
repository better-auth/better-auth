`OAuth2` `OIDC`

[Client-Initiated Backchannel Authentication](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html) (CIBA) is an OpenID Connect flow for **decoupled authentication**: the client that wants tokens is not where the user signs in. The client names the user, your server sends that user a link, the user approves on their own phone or laptop, and the client then collects tokens. The client never redirects the user and never sees their credentials.

Use it when the client already knows who it is acting for but cannot show that person a browser:

* An AI agent or backend job that needs a person's approval before it acts for them.
* A call-center or support tool where the operator starts a sign-in the customer approves on their phone.
* A kiosk or terminal that should never collect the user's credentials.

If the client can show a code or a QR code to a person in front of it, use the [device authorization grant](./device-authorization) instead.

The plugin extends [`@better-auth/oauth-provider`](./oauth-provider) and requires `oauthProvider()` and `jwt()`. It supports CIBA poll mode.

## How the flow works

1. The **client** calls `POST /oauth2/bc-authorize` with its credentials, the scopes it wants, and a `login_hint` naming the user. It receives an `auth_req_id` and a polling `interval`.
2. Your **server** reaches the user through your `sendNotification` callback, by email or push notification, with a link to the provider.
3. The **user** opens the link, signs in if needed, and approves or denies on your consent page. They land on your `resultPage`.
4. The **client** polls `POST /oauth2/token` with the `auth_req_id`. It receives `authorization_pending` until the user decides, then the tokens or `access_denied`.

## Installation

    @better-auth/ciba

  </Step>

  <Step>
    ### Add the plugin to the server

    Add `ciba()` after `oauthProvider()` and `jwt()`. `sendNotification` sends the user the link, and `resultPage` is the page they land on after deciding.

    ```ts title="auth.ts"
    import { betterAuth } from "better-auth";
    import { jwt } from "better-auth/plugins";
    import { oauthProvider } from "@better-auth/oauth-provider";
    import { ciba } from "@better-auth/ciba"; // [!code highlight]

    export const auth = betterAuth({
      plugins: [
        jwt(),
        oauthProvider({
          loginPage: "/login",
          consentPage: "/consent",
          scopes: ["openid", "profile", "email"],
        }),
        ciba({ // [!code highlight]
          resultPage: "/ciba", // [!code highlight]
          sendNotification: async ({ user, clientName, bindingMessage, url }) => { // [!code highlight]
            await sendEmail({ // [!code highlight]
              to: user.email, // [!code highlight]
              subject: `${clientName ?? "An application"} wants to act for you`, // [!code highlight]
              text: `${bindingMessage ?? ""}\nReview the request: ${url}`, // [!code highlight]
            }); // [!code highlight]
          }, // [!code highlight]
        }), // [!code highlight]
      ],
    });
    ```
  </Step>

  <Step>
    ### Migrate the database

    The plugin adds a `cibaRequest` model. Run `npx auth@latest migrate` with the built-in Kysely adapter, or run `npx auth@latest generate` and apply the schema with your ORM.
  </Step>

  <Step>
    ### Show the binding message on your consent page

    The link opens your existing `consentPage`. For a CIBA request, its query carries `ciba_request_id`, `client_id`, `scope`, and the client's `binding_message` when it sent one. Show the binding message as plain text next to the client and scopes, so the user can check that it matches what the client displays.

    ```ts title="consent-page.ts"
    const params = new URLSearchParams(location.search);
    const bindingMessage = params.get("binding_message"); // only for CIBA requests
    ```

    Accept or deny with `oauth2.consent` as you already do for authorization requests.
  </Step>

  <Step>
    ### Build the result page

    After the user decides, they land on `resultPage` with `status=approved` or `status=denied`. When the link is invalid, expired, already used, or for another account, they land there with `error` and `error_description` instead. Tell them they can return to the app that asked.
  </Step>
</Steps>

## Register a client

A client can start CIBA requests only when it is registered for the CIBA grant type and its `metadata` declares `backchannel_token_delivery_mode: "poll"` (CIBA §4). Only server-side client management can set `metadata`, so clients from open dynamic registration or Client ID Metadata Documents cannot send your users sign-in requests. The client must authenticate, so give it a `client_secret` or another confidential authentication method.

```ts title="register-client.ts"
import { CIBA_GRANT_TYPE } from "@better-auth/ciba";

const client = await auth.api.adminCreateOAuthClient({
  headers, // an authenticated admin session
  body: {
    client_name: "Support Agent",
    grant_types: [CIBA_GRANT_TYPE], // "urn:openid:params:grant-type:ciba"
    metadata: { backchannel_token_delivery_mode: "poll" },
  },
});
// Store client.client_id and client.client_secret for the agent.
```

## Request tokens from the client

The client starts a request, shows its `binding_message` to whoever is watching, then polls the token endpoint. Both calls are form-encoded and authenticate the client; this example uses HTTP Basic.

```ts title="agent.ts"
const basic = btoa(`${clientId}:${clientSecret}`);
const form = (body: Record<string, string>) => ({
  method: "POST",
  headers: {
    authorization: `Basic ${basic}`,
    "content-type": "application/x-www-form-urlencoded",
  },
  body: new URLSearchParams(body),
});

// 1. Start the request.
const request = await fetch(
  "https://auth.example.com/api/auth/oauth2/bc-authorize",
  form({
    scope: "openid profile",
    login_hint: "ada@example.com",
    binding_message: "Code 4821", // show this in the client too
  }),
).then((r) => r.json());
// => { auth_req_id, expires_in, interval }

// 2. Poll until the user decides.
let interval = request.interval;
for (;;) {
  await new Promise((resolve) => setTimeout(resolve, interval * 1000));
  const body = await fetch(
    "https://auth.example.com/api/auth/oauth2/token",
    form({
      grant_type: "urn:openid:params:grant-type:ciba",
      auth_req_id: request.auth_req_id,
    }),
  ).then((r) => r.json());
  if (body.error === "authorization_pending") continue;
  if (body.error === "slow_down") {
    interval += 5; // CIBA §11: wait at least 5 more seconds from now on
    continue;
  }
  if (body.error) throw new Error(body.error); // access_denied, expired_token, ...
  return body; // { access_token, token_type, expires_in, id_token, ... }
}
```

To get a JWT access token for an API, send its [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) `resource` with the request, as with other grants. A DPoP proof on the token poll binds the token to the client's key.

## What the user sees

The link points to `/oauth2/authorize?ciba_request_id=<id>`, so the request runs through the provider's own pages:

1. A signed-out user goes to `loginPage` first. Nothing about the request is shown before sign-in.
2. [`postLogin`](/docs/plugins/oauth-provider#post-login-screen) runs as it does for an authorization request, and tokens carry the `referenceId` that `consentReferenceId` returns.
3. `consentPage` always opens, even for a client with `skip_consent` or a stored consent, because the user must confirm each request. The user can narrow the scopes there.
4. The decision is recorded only for the user the `login_hint` named. Anyone else who opens the link, signed in as another account, lands on `resultPage` with an error, and the request stays pending for the right user.

A denial is final: the client's next poll returns `access_denied`, and the link stops working. The ID token's `auth_time` is the creation time of the approving user's session.

## Endpoints

### `POST /oauth2/bc-authorize`

Starts a request. It accepts only `application/x-www-form-urlencoded` (CIBA §7.1), authenticates the client, and returns `auth_req_id`, `expires_in`, and `interval`. Each IP address can start 10 requests per minute.

| Parameter          | Required | Description                                                                                                          |
| ------------------ | -------- | -------------------------------------------------------------------------------------------------------------------- |
| `scope`            | yes      | Space-delimited scopes. Must include `openid`.                                                                       |
| `login_hint`       | yes      | Identifies the user, by email unless you set `resolveUser`.                                                          |
| `binding_message`  | no       | Up to 64 characters of plain text, in any script, shown in the notification, on the consent page, and by the client. |
| `requested_expiry` | no       | Requested lifetime in seconds, a positive integer. Capped at `expiresIn`.                                            |
| `resource`         | no       | One or more resource indicators the token is bound to.                                                               |

### `POST /oauth2/token`

The provider's token endpoint. With `grant_type=urn:openid:params:grant-type:ciba` and the `auth_req_id`, it returns the tokens once the user approves, or one of the errors below. Each `auth_req_id` issues tokens once.

## Errors

The backchannel endpoint returns these [CIBA §13](https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html#auth_error_response) errors:

| Error                     | Meaning                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `invalid_request`         | A required parameter is missing or malformed, or the request uses a hint other than `login_hint`.        |
| `invalid_scope`           | `scope` does not include `openid`, or the client may not request it.                                     |
| `invalid_client`          | The client did not authenticate.                                                                         |
| `unauthorized_client`     | The client is not registered for the CIBA grant with `backchannel_token_delivery_mode: "poll"`.          |
| `invalid_binding_message` | The binding message is longer than 64 characters or contains control or invisible formatting characters. |
| `unknown_user_id`         | No user matches the `login_hint`.                                                                        |
| `invalid_target`          | A `resource` is malformed or unknown.                                                                    |

The token poll returns:

| Error                   | Meaning                                                                       |
| ----------------------- | ----------------------------------------------------------------------------- |
| `authorization_pending` | The user has not decided yet. Keep polling.                                   |
| `slow_down`             | Polling faster than `interval`. Wait at least 5 more seconds between polls.   |
| `access_denied`         | The user denied the request.                                                  |
| `expired_token`         | The request expired before the user decided.                                  |
| `invalid_grant`         | The `auth_req_id` is unknown, belongs to another client, or was already used. |

## Schema

The plugin adds one model, `cibaRequest`:

| Field            | Type      | Description                                                                                                                 |
| ---------------- | --------- | --------------------------------------------------------------------------------------------------------------------------- |
| `authReqId`      | string    | The `auth_req_id`, hashed like the provider's tokens. The raw value is never stored.                                        |
| `clientId`       | string    | The client that started the request.                                                                                        |
| `userId`         | string    | The user the `login_hint` named, the only user who can decide.                                                              |
| `scope`          | string    | The requested scopes, narrowed to the approved ones on approval.                                                            |
| `bindingMessage` | string    | The optional binding message.                                                                                               |
| `resources`      | string\[] | The optional resource indicators.                                                                                           |
| `status`         | string    | `pending`, `approved`, or `denied`. A request is deleted when tokens are issued or the client learns of a denial or expiry. |
| `referenceId`    | string    | The consent reference recorded on approval, such as an organization.                                                        |
| `authTime`       | date      | Creation time of the approving session, issued as `auth_time`.                                                              |
| `lastPolledAt`   | date      | When the client last polled.                                                                                                |
| `expiresAt`      | date      | When the request expires.                                                                                                   |
| `createdAt`      | date      | When the request was created.                                                                                               |

## Security

* **Only clients you register can reach your users.** Each request notifies a person, so the plugin requires client authentication, the CIBA grant, and poll registration in server-set `metadata`, and limits each IP address to 10 requests per minute. A registered client can still learn whether an email belongs to a user from `unknown_user_id`, as CIBA §13 specifies.
* **Consent is always shown, and only the named user can decide.** A user who receives a request they did not expect can deny it, and someone else who gets hold of the link cannot approve or deny it.
* **The binding message ties the two devices together.** Ask clients to send a short, random `binding_message` and to display it, so the user can tell their request apart from one someone else started at the same moment. Render it as text.
* **Tokens are issued once.** An approved request is claimed and deleted in one atomic step, so of two concurrent polls only one receives tokens. The `auth_req_id` is stored hashed.

## Current limitations

* Ping and push delivery are not supported.
* Only `login_hint` is supported; `id_token_hint` and `login_hint_token` are rejected with `invalid_request`.
* `user_code`, signed authentication requests, `acr_values`, and `authorization_details` are not supported. `acr_values` are ignored.
* There is no per-user limit on requests; the limit applies per IP address.
