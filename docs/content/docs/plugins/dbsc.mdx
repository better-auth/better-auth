Malware that steals browser cookies can copy a user's session cookie and replay it from another machine. `HttpOnly` and `Secure` do not stop this, because the malware reads the cookie store directly. The DBSC plugin uses [Device Bound Session Credentials](https://w3c.github.io/webappsec-dbsc/) to bind each session to a private key that the browser keeps in the device's secure hardware. Once a session is bound, Better Auth accepts it only together with a short-lived cookie that the browser renews by signing a challenge with that key. The key never leaves the device, so a copied cookie stops working on any other machine.

## Browser support

Chrome supports Device Bound Session Credentials on Windows from Chrome 145 and on macOS from Chrome 147. Google turns the feature on gradually, so some users on those versions do not have it yet. In every other browser, and on devices without secure key storage, sessions stay unbound and work exactly as they do without the plugin.

Chrome only registers keys over HTTPS. Sessions created on a plain `http://localhost` development server are never bound.

## How it works

1. A user signs in. The sign-in response offers the browser a registration challenge.
2. A supporting browser creates a key pair and sends the public key, signed over the challenge, to `/dbsc/register`.
3. Better Auth stores the public key on the session and sets a bound cookie that expires after `boundCookieMaxAge` seconds, 10 minutes by default.
4. Before the bound cookie expires, the browser signs a challenge from Better Auth with the private key and sends it to `/dbsc/refresh`. It receives a new bound cookie and the challenge for its next refresh.

Some sign-ins cannot carry the registration offer to the browser directly: social and SSO sign-ins that end in a redirect, and sign-ins that run on your server, such as a server action. For those, Better Auth sets a short-lived cookie, and the next same-site browser request to Better Auth makes the offer instead, usually the `/get-session` call the client makes after sign-in. If the browser does not register within 5 minutes, the session stays unbound.

A sign-in on your server is offered registration only when you pass the incoming request's headers, as in `auth.api.signInEmail({ body, headers: await headers() })`. Without them, Better Auth cannot tell the call came from a browser, and the session stays unbound.

## What a bound session requires

Once a session is bound, every session lookup requires its bound cookie. This covers `/get-session`, `auth.api.getSession`, every endpoint that requires a session, and the multi-session and admin plugins. Without a valid bound cookie, the session token is treated as signed out:

* A copied session cookie, sent on its own or as a bearer token, returns no session.
* A copied cookie-cache cookie returns no session.
* A copied session cookie cannot end the session.

Sessions are only treated as signed out, not deleted, so a request that is missing the bound cookie does not end the user's session. When a user signs out while their browser is missing the bound cookie, for example right after a failed refresh, Better Auth clears that browser's session cookies and keeps the session on the server until it expires.

When your server forwards a browser request to `auth.api.getSession`, pass the request's full `Cookie` header. A request that carries only the session token is rejected for a bound session.

## Limits

Device binding protects against a copied cookie being used after sign-in, on another device. It does not protect against:

* Malware that is already running on the device when the user signs in. It can register its own key.
* Someone who copies the browser's cookies before the browser registers its key, which can take up to 5 minutes after a redirect sign-in, and registers a key of their own first. The user's browser is then signed out and must sign in again. A copy that does not register first stops working once the browser registers.
* Malware or a script running in the user's browser while the user is signed in. It can make requests that the browser signs.
* A copied bound cookie, for up to `boundCookieMaxAge`, which defaults to 10 minutes.

Some parts of Better Auth are not bound:

* `getSessionCookie` and `getCookieCache` only read cookies, for fast checks in middleware. They do not check the binding, so use `auth.api.getSession` for anything that needs a verified session.
* Credentials created from a session live on their own, such as JWTs from the [JWT plugin](/docs/plugins/jwt), API keys, and OAuth tokens. Keep their lifetimes short.
* With the cookie cache enabled, a session can be served from a cached copy made before the key was registered. That copy expires after `session.cookieCache.maxAge`.
* With `secondaryStorage`, Better Auth rewrites a stored session as a whole. A write to the same session at the moment the browser registers, such as a profile update, can drop the saved key. That session then works as an ordinary session until it ends.
* Sessions created by [admin impersonation](/docs/plugins/admin) are never bound.
* Removing the plugin turns bound sessions back into ordinary sessions, which a copied session cookie can use again. Revoke existing sessions when you remove it.

## Deployment

**Separate app and auth hosts.** When your app runs on a different host than Better Auth on the same site, such as `app.example.com` calling `api.example.com`, add the app's origin to `trustedOrigins`, as `https://app.example.com` or `*.example.com`. Chrome refreshes a bound cookie only for requests started from Better Auth's own origin or from hosts the session lists, and the plugin lists the trusted origins on the same site as Better Auth. Without the entry, users are signed out when the bound cookie expires.

**Links from other sites.** When a user follows a link from another site, such as an email, and the bound cookie has expired, Chrome sends that first page request without it. Your server sees no session for that request. The next request the page makes to Better Auth, such as the client's `/get-session` call, renews the cookie. If your server redirects signed-out visitors to a sign-in page, have that page send users who turn out to be signed in back to where they were going.

**Rate limiting.** The plugin allows 120 requests per minute from each client IP to each of `/dbsc/register` and `/dbsc/refresh`. A refresh usually takes one request, or two when the browser was idle longer than `boundCookieMaxAge`. Users behind one shared IP, such as an office network, count against the same limit. If Better Auth cannot read the client IP behind your proxy, every client shares one limit. Configure [`advanced.ipAddress`](/docs/concepts/rate-limit) so each client is counted separately. When Chrome's refresh is rate limited, it sends the request without the bound cookie, and the user appears signed out for that request.

**Several accounts in one browser.** With the [multi-session plugin](/docs/plugins/multi-session), each signed-in account is bound and refreshed separately. Chrome signs at most 6 times every 9 minutes for one site. With four or more bound accounts in one browser, some requests go out without a bound cookie and those accounts appear signed out until a later refresh succeeds.

**Proxies and CDNs.** The refresh endpoint answers with status `403` and a `Secure-Session-Challenge` header when it needs a signature. Make sure your proxy, CDN, or firewall passes both through unchanged, and forwards the `Secure-Session-Response` and `Sec-Secure-Session-Id` request headers.

**Unsupported configurations.** The plugin throws at startup with:

* No database or secondary storage. The device key is stored with the session.
* `advanced.crossSubDomainCookies`. Sharing a bound session across subdomains is not supported yet.
* `advanced.defaultCookieAttributes.partitioned`. Chrome cannot bind partitioned cookies.

## Options

`boundCookieMaxAge` <span className="opacity-70">`number`</span>

How long a bound cookie stays valid, in seconds. Defaults to `600`. Chrome replaces the cookie about two minutes before it expires, so this is also the longest a copied bound cookie keeps working. The minimum is `300`: shorter values make Chrome sign on almost every request and exhaust its signing limit.

`schema` <span className="opacity-70">`object`</span>

Renames the plugin's session field. See [Schema](#schema).
