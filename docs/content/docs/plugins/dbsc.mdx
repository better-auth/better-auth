Malware that steals browser cookies can copy a user's session cookie and replay it from another machine. `HttpOnly` and `Secure` do not stop this, because the malware reads the cookie store directly. The DBSC plugin uses [Device Bound Session Credentials](https://w3c.github.io/webappsec-dbsc/) to bind each session to a private key that the browser keeps in the device's secure hardware. Once a session is bound, Better Auth accepts it only together with a short-lived cookie that the browser renews by signing a challenge with that key. The key never leaves the device. A copied cookie therefore stops working on any other machine.

## When to use it

Use the plugin when a stolen session would do real harm, such as in admin consoles or apps that hold payment or health data. Browsers without support keep ordinary sessions.

Before you turn it on, check its requirements, costs, and limits:

* Sessions are bound only over HTTPS. The plugin needs a database or secondary storage.
* While a bound browser is in use, it renews its cookie about every 8 minutes by default. Each renewal reads the session and stores a challenge in the verification table or secondary storage. Every browser sign-in also stores a registration challenge.
* With the [cookie cache](/docs/concepts/session-management#cookie-cache) on, Better Auth reads an unbound session from storage on each lookup for about the session's first 5 minutes plus the cache's lifetime. A cached copy made before the browser registered is then refused once it registers.
* It cannot run with `advanced.crossSubDomainCookies` or partitioned cookies.
* It does not stop malware that runs on the device while the user signs in or uses the app. See [Limits](#limits).

## Browser support

Chrome supports Device Bound Session Credentials on Windows from Chrome 145 and on macOS from Chrome 147. Google turns the feature on gradually, so some users on those versions do not have it yet. In every other browser, and on devices without secure key storage, sessions stay unbound and work exactly as they do without the plugin.

Chrome only registers keys over HTTPS. Sessions created on a plain `http://localhost` development server are never bound.

## Binding and renewing a session

1. A user signs in. The sign-in response offers the browser a registration challenge.
2. A supporting browser creates a key pair and sends the public key, signed over the challenge, to `/dbsc/register`.
3. Better Auth stores the public key on the session and sets a bound cookie that expires after `boundCookieMaxAge` seconds, 10 minutes by default.
4. Before the bound cookie expires, the browser signs a challenge from Better Auth with the private key and sends it to `/dbsc/refresh`. It receives a new bound cookie and the challenge for its next refresh.

Every browser sign-in creates a new session, which is offered registration. This includes signing in again to pass a fresh-session check.

Some sign-ins cannot carry the registration offer to the browser directly: social and SSO sign-ins that end in a redirect, and sign-ins that run on your server, such as a server action. For those, Better Auth sets a short-lived cookie, and the next same-site browser request to Better Auth makes the offer instead, usually the `/get-session` call the client makes after sign-in. If the browser does not register within 5 minutes, the session stays unbound.

A sign-in on your server is offered registration only when you pass the incoming request's headers, as in `auth.api.signInEmail({ body, headers: await headers() })`. Without them, Better Auth cannot tell the call came from a browser, and the session stays unbound.

## What a bound session requires

Once a session is bound, every session lookup requires its bound cookie. This covers:

* `/get-session`, `auth.api.getSession`, and every endpoint that requires a session.
* The multi-session and admin plugins.
* Redeeming a token from the [one-time token plugin](/docs/plugins/one-time-token). The redeeming request must carry the bound cookie. A token handed to another browser or device is refused with `Invalid token`.
* Finding the browser's session during logout with the [OAuth provider plugin](/docs/plugins/oauth-provider).

Without a valid bound cookie, the session token is treated as signed out:

* A copied session cookie, sent on its own or as a bearer token, returns no session.
* A copied cookie-cache cookie returns no session.
* A copied session cookie cannot end the session.

Sessions are only treated as signed out, not deleted, so a request that is missing the bound cookie does not end the user's session. When a user signs out while their browser is missing the bound cookie, for example right after a failed refresh, Better Auth clears that browser's session cookies and keeps the session on the server until it expires.

When your server forwards a browser request to `auth.api.getSession`, pass the request's full `Cookie` header. A request that carries only the session token is rejected for a bound session.

## Checking whether a session is bound

The session's `dbscPublicKey` field tells you whether the session is bound. You can use it to show users which of their sessions are protected. Add the [client plugin](#add-the-client-plugin-optional) to read the field with the right type:

```ts title="session-status.tsx"
const { data } = authClient.useSession()
const isBound = data?.session.dbscPublicKey != null
```

What the field means depends on where you read it:

* On the session of the current request, from `getSession`, `useSession`, or an endpoint that requires a session, a value means the request carried a valid bound cookie.
* In session lists, such as `listSessions` or the admin plugin's session list, a value means the browser registered a key for that session. Better Auth does not check the bound cookies of the other sessions in the list.
* `null` is the normal state in browsers without support, and right after sign-in until the browser registers.

Present a bound session as extra protection, and do not label unbound sessions as unsafe. Most users cannot change their browser's support. For the same reason, requiring a bound session for an action locks out every browser without support.

## Limits

Device binding protects against a copied cookie being used after sign-in, on another device. It does not protect against:

* Malware that is already running on the device when the user signs in. It can register its own key.
* Someone who copies the browser's cookies before the browser registers its key, and registers a key of their own first. After a redirect sign-in, the browser can take up to 5 minutes to register. The user's browser is then signed out and must sign in again. A copy that does not register first stops working once the browser registers.
* Malware or a script running in the user's browser while the user is signed in. It can make requests that the browser signs.
* A copied bound cookie, for up to `boundCookieMaxAge`, which defaults to 10 minutes.

Some parts of Better Auth are not bound:

* `getSessionCookie` and `getCookieCache` only read cookies, for fast checks in middleware. They do not check the binding, so use `auth.api.getSession` for anything that needs a verified session.
* Credentials created from a session, such as JWTs from the [JWT plugin](/docs/plugins/jwt), API keys, and OAuth tokens, are not bound. Once a session is bound, creating one with the session cookie requires the bound cookie. The credential itself then works wherever it is sent. Keep JWT lifetimes short.
* With the API key plugin's `enableSessionForAPIKeys`, a request that carries an API key gets a session built from the key. The DBSC plugin does not check that session. Anyone who holds the key gets the session on any device, as with any other request made with the key.
* With `secondaryStorage`, Better Auth rewrites a stored session as a whole. A write to the same session at the moment the browser registers, such as a profile update, can drop the saved key. That session then works as an ordinary session until it ends.
* Sessions created by [admin impersonation](/docs/plugins/admin) are never bound.
* Removing the plugin turns bound sessions back into ordinary sessions, which a copied session cookie can use again. Revoke existing sessions when you remove it.

## Deployment

**Separate app and auth origins.** When your app runs on a different host or port than Better Auth on the same site, such as `app.example.com` calling `api.example.com`, add the app's exact origin, such as `https://app.example.com`, to `trustedOrigins`. Avoid a wildcard such as `*.example.com`. Trusted origins can receive redirects and pass the CSRF origin check, and a wildcard extends that trust to every subdomain, including ones you do not control. Chrome refreshes a bound cookie only for requests started from Better Auth's own origin or from hosts the session lists, and the plugin lists the trusted origins on the same site as Better Auth. Without the entry, users are signed out when the bound cookie expires.

**Links from other sites.** When a user follows a link from another site, such as an email, and the bound cookie has expired, Chrome sends that first page request without it. Your server sees no session for that request. The next request the page makes to Better Auth, such as the client's `/get-session` call, renews the cookie. If your server redirects signed-out visitors to a sign-in page, have that page send users who turn out to be signed in back to where they were going.

**OAuth provider.** With the [OAuth provider plugin](/docs/plugins/oauth-provider), client apps on other sites send users to `/oauth2/authorize`. If the bound cookie has expired, Chrome sends that request without it. The user then appears signed out:

* An interactive request shows your login page, and the user signs in again. On that page, do not send users who turn out to be signed in back to `/oauth2/authorize`. A request that asks for a new sign-in, with `prompt=login` or `max_age`, would then loop.
* A request with `prompt=none` returns `login_required` to the client app. The client app must then start an interactive request.

**Rate limiting.** The plugin allows 120 requests per minute from each client IP to each of `/dbsc/register` and `/dbsc/refresh`. A refresh usually takes one request, or two when the browser was idle longer than `boundCookieMaxAge`. Users behind one shared IP, such as an office network, count against the same limit. If Better Auth cannot read the client IP behind your proxy, every client shares one limit. To count each client separately, set [`advanced.ipAddress.ipAddressHeaders`](/docs/reference/security#ip-address-headers) to the header that your proxy overwrites on every request. When Chrome's refresh is rate limited, it sends the request without the bound cookie, and the user appears signed out for that request.

**Several accounts in one browser.** With the [multi-session plugin](/docs/plugins/multi-session), each signed-in account is bound and refreshed separately. Chrome signs at most 6 times every 9 minutes for one site. With four or more bound accounts in one browser, some requests go out without a bound cookie and those accounts appear signed out until a later refresh succeeds.

**Proxies and CDNs.** The refresh endpoint answers with status `403` and a `Secure-Session-Challenge` header when it needs a signature. Make sure your proxy, CDN, or firewall passes both through unchanged, and forwards the `Secure-Session-Response` and `Sec-Secure-Session-Id` request headers.

**Unbound sessions.** Sessions created before you enabled the plugin stay unbound until they end. So do sessions in browsers without support, and sessions whose browser did not register in time. To limit how long an unbound session lasts, add a check of your own:

```ts title="auth.ts"
import { betterAuth } from "better-auth"
import type { BetterAuthPlugin } from "better-auth"
import { dbsc } from "@better-auth/dbsc"

const maxUnboundAge = 30 * 24 * 60 * 60 * 1000 // 30 days

const limitUnboundSessions = {
    id: "limit-unbound-sessions",
    validateSession: ({ session }) =>
        session.dbscPublicKey != null ||
        new Date(session.createdAt).getTime() > Date.now() - maxUnboundAge,
} satisfies BetterAuthPlugin

export const auth = betterAuth({
    plugins: [dbsc(), limitUnboundSessions],
})
```

The check applies to every session that has no key, not only to browsers without support. It also ends sessions that cannot be bound, such as sessions of native and desktop apps and of clients that sign in with a bearer token.

Adding the check has these effects:

* When you add the check, every unbound session older than the limit is signed out at its next request.
* Users whose sessions cannot be bound then sign in again every 30 days.
* A sign-in in a supporting browser gets a new chance to register.

Choose a limit that those users can accept.

**Checking your setup.** Before you rely on the plugin in production, test it on an HTTPS staging deployment:

1. Set `boundCookieMaxAge: 300`, and sign in with a version of Chrome that supports Device Bound Session Credentials.
2. Check that the session's `dbscPublicKey` is set. If it is not, check that a response carried a `Secure-Session-Registration` header: the sign-in response, or for social, SSO, and server-side sign-ins, the next `/get-session` response. If one did, check your access logs for a `/dbsc/register` request. If there is none, this browser did not register, for example because Google has not turned the feature on for it yet.
3. Keep using the app for more than 5 minutes. Check your server or proxy access logs for `/dbsc/refresh` requests, and check that you stay signed in.

**Finding why users are signed out.** Set `logger: { level: "debug" }` in your auth config. Better Auth then logs each time a bound session arrives without a valid bound cookie, and each time a refresh ends a browser's session.

**Unsupported configurations.** The plugin throws at startup with:

* No database or secondary storage. The device key is stored with the session.
* `advanced.crossSubDomainCookies`. Sharing a bound session across subdomains is not supported yet.
* `advanced.defaultCookieAttributes.partitioned`. Chrome cannot bind partitioned cookies.

## Configuration

`boundCookieMaxAge` <span className="opacity-70">`number`</span>

How long a bound cookie stays valid, in seconds. Defaults to `600`. Chrome replaces the cookie about two minutes before it expires. The value is also the longest time a copied bound cookie keeps working. The minimum is `300`: shorter values make Chrome sign on almost every request and exhaust its signing limit.

`schema` <span className="opacity-70">`object`</span>

Renames the plugin's session field. See [Schema](#schema).
