Fix the OAuth revocation endpoint to answer 200 for invalid tokens per RFC 7009 section 2.2. The `/oauth2/revoke` endpoint returned 400 `invalid_request` when the submitted token was unknown, already revoked, or looked up with a mismatched `token_type_hint`. The RFC requires a 200 response in all those cases — the client cannot handle such errors, and the revocation goal is already achieved. `unsupported_token_type` (self-contained JWT access tokens) and `invalid_client` still surface as errors. A wrong `token_type_hint` no longer gates the search either: the hinted lookup failing now extends across the other supported token type, so the token is actually revoked instead of the request failing with 400. The 400 classification is spelling-independent (a `formatRefreshToken.decrypt` throwing either `APIError("BAD_REQUEST")` or `APIError(400)` continues the search), and unexpected decrypt failures (a plain `Error`, e.g. a key store outage) now surface as a 500 instead of being masked as a 200 - matching the introspection endpoint's treatment of the same failure - so a client never receives a success answer while its token is still active.
