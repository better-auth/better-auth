The OAuth provider can now serve pushed authorization requests (RFC 9126). Set `pushedAuthorizationRequests: { enabled: true }` on `oauthProvider()`, and clients can send their authorization parameters to `POST /oauth2/par` with their usual client authentication. The endpoint validates them as `/oauth2/authorize` would and returns a `request_uri` for that client alone. The client has 60 seconds by default to send the user to `/oauth2/authorize` with it. The user can then reload the authorization URL and take as long as `codeExpiresIn` to sign in, and the `request_uri` issues one authorization code. Discovery advertises `pushed_authorization_request_endpoint`. A DPoP proof sent with the push binds the authorization code to that key (RFC 9449 §10.1), and a pushed `dpop_jkt` that names another key fails with `invalid_dpop_proof`.

To require pushed requests from every client, also set `required: true` in `pushedAuthorizationRequests`. To require them from one client, register it with `require_pushed_authorization_requests: true`. That registration fails with `invalid_client_metadata` unless the server serves `/oauth2/par` (PAR enabled and `grantTypes` includes `authorization_code`) or you set `requestUriResolver`. A plain authorization request then fails with `invalid_request`, while login, consent, and other screens keep working. When you also use `requestUriResolver`, the authorize endpoint looks up values that `/oauth2/par` issued first and calls your resolver for any other value, including one that expired or already issued its code.

The per-client policy adds a `requirePushedAuthorizationRequests` column to the `oauthClient` table, even if you leave PAR off. Apply it before deploying, because requests fail until the column exists: run `npx auth@latest migrate` with the built-in Kysely adapter, or run `npx auth@latest generate` and apply the schema with your ORM.
