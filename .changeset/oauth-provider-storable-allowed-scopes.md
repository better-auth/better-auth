`allowedScopes` now has one storable contract across adapters:

- In plugin configuration, omit `allowedScopes` (or pass `null`) to allow every requested scope. An empty array (`[]`) in config is rejected at startup with guidance to use `disabled: true` to prevent ambiguity with blocking access.
- In `adminCreateOAuthResource`, omitting `allowedScopes` allows every requested scope (unrestricted). Passing explicit `null` to either admin endpoint resets to unrestricted, while omitting `allowedScopes` on `adminUpdateOAuthResource` leaves the stored allowlist unchanged. Passing `[]` to either endpoint is rejected, mirroring the config validation. Use `disabled: true` to stop issuing tokens for a resource.
- A non-empty array is an allowlist; scopes outside it are removed and an empty intersection is rejected with `invalid_scope`.
- Newly created or seeded unrestricted resources are stored as `allowedScopes: []` instead of `null`, enabling consistent storability across adapters (such as Prisma on PostgreSQL where list columns cannot store `null`). Admin responses serialize an unrestricted allowlist as `null`, which echoes back cleanly.
- Rows created before this change remain as stored (which may hold `allowedScopes: null` in SQL databases); both `null` and `[]` are treated as unrestricted at token issuance and both serialize as `null` on the wire. Passing an explicit `[]` to the admin endpoints is rejected. Omit the field or pass `null` instead. Updating a row with `null` normalizes the stored value to `[]`.

**Migration:** resources whose stored `allowedScopes` is empty currently refuse every token. This includes Prisma rows where SQL `NULL` was read back as `[]`. After upgrading, those resources allow every requested scope, so the change fails open. Before the first 1.8 process starts, find the stored resources with an empty `allowedScopes` and set `disabled: true` on each one that relied on denying every scope, or give it real scopes. 1.8 admin responses return `null` for a stored `[]`, so list these rows with the 1.7 `adminListOAuthResources` endpoint or a direct database query. Once 1.8 writes `[]` for unrestricted resources, even a database query cannot tell those rows from legacy deny-all rows. A disabled resource fails every token request with `invalid_target` and issues no new tokens. Access tokens already issued keep verifying until they expire, and refresh tokens for the resource fail with `invalid_target`. A deployment that runs 1.7 and 1.8 together reads a stored `[]` differently: 1.7 denies every scope and 1.8 allows every scope. Existing rows are not rewritten and no schema migration is required. Configured `resources` entries with `allowedScopes: []` fail validation at startup, and the `mcp()` resource no longer needs the explicit workaround.
